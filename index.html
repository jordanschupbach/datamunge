    One C to rule them all, one C to find them, one C to bring them all and in the darkness...

    Datamunge is a C/C++ project that has (nearly) automatically generated bindings for a variety of languages, including Python, R, JavaScript, Lua, PHP, Java, C#, D and Go. It is merely meant to be used as a kickstart template for similar projects that need to provide bindings to multiple languages. As such, it is permissively licensed under the Unlicense.

    It uses CMake as the build system, and Just as a task runner. The project maintains a nix flake for easy development and testing.

    To demonstrate nontrivial examples, it provides simple implementations of some common datastructures (e.g. dynamic array) written in C and bound to all targeted binding languages. It is meant to be installable from any of the supported languages' package managers (e.g. PyPI for Python, CRAN for R, npm for JavaScript, etc). Thus, it also provides build configurations for these package managers along with necessary packaging files for each language. While this makes the project more complex, it also means that there is a single source of truth for the core implementation, and that any bug fixes or improvements can be made in one place and propagated to all bindings.

    🚗 Test drive

    ❄️ NixOS

    The easiest way to test drive the project is to use the provided Nix flake. You can use the following command to enter a development shell with all dependencies:

    nix develop

    If Zsh completion mixes Homebrew and Nix versions of just, source scripts/just-completion.zsh after compinit in your Zsh startup configuration. It selects the active executable's completion protocol again whenever direnv changes PATH. This prevents newer dynamic completion loaders from executing an older just's default recipe when you press Tab.

    To build the project

    just build

    just build and just build-cpp build the core in Release mode. Standalone CMake builds also default to Release when no build type is selected; use -DCMAKE_BUILD_TYPE=Debug for an explicit debug build. The TensorFlow comparison uses a separate Release build of both the core and benchmark driver; see the comparison workflow. All performance plans and TensorFlow/native comparison tables live in PERFORMANCE.md.

    to run tests:

    just test

    to build examples:

    just examples

    to run TARGET example:

    just run TARGET=example_name

    Renaming this template

    This repo is intended to be cloned and renamed. All occurrences of the project name are expected to be datamunge (lowercase) unless casing is required by a particular ecosystem.

    • Rename everything (file contents + paths): ./rename_datamunge <new_project_name>
      • <new_project_name> must be lowercase (a-z, 0-9, _ or -)

    Bindings

    The CAD and 3D modelling guide covers dm::cad solids, the ported mep kernel, model formats and offline rendering. The Seeed DevArm report includes C++/Python/R examples using the real Seeed DevArm CAD and visual mesh files.

    The native CPU game/simulation library and batched physical RL tasks are described in the simulation guide. GPU compute dispatch is optional, with native scene import, Courier behaviors and offscreen Vulkan rendering available. Full NN/GPU physics integration remains in progress.

    See the binding workflow and audit for source packages, regeneration, and the current language coverage.

    Each binding lives under src/ (e.g. src/rustdatamunge/, src/datamungego/, src/datamungeguile/), with SWIG generator inputs kept alongside each binding (typically src/<binding>/swig/). The APL, C#, Common Lisp, Fortran, Go, Java, Julia, OCaml, Octave, Ruby and Tcl bindings are generated by Rosetta instead, from the Clang AST (src/datamunge<lang>/rosetta/); their docstrings (⍝ comments in the APL script, XML doc comments in C#, FORD !> comments in Fortran, godoc comments in Go, Javadoc in Java, .m help text in Octave, YARD comments in Ruby, commented proc/oo::class stubs in Tcl) come from the Doxygen comments. The tensor/NN facade is currently exposed in Python and R; the other bindings cover their existing core APIs. The C/C++ core remains the single source of truth; bindings are (re)generated via the just prebuild-* / just build-* workflows.

    CNN and autoencoder examples (sections 1 and 2) are available in C++ and through Python/SWIG.

    The NN language rewrite covers 414 canonical C++ examples across foundations, CNNs, autoencoders, generative models, recurrent networks, attention and RL. Actual implementations use the functional SWIG API (pydatamunge.nn / datamungerNN::nn) with models and loops written in each language. Track completed ports and validation in the migration ledger with just nn-language-status; compiled reference wrappers do not count as ports.

    Run a completed port with just python-example NAME epochs=5 or just r-example NAME epochs=5. Both commands reject unported examples; use just run-nn NAME for the canonical C++ report. Classification ports print a confusion matrix. See migration notes and the Python / R example docs.
