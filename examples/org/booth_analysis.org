#+begin_abstract
Multiplying two's-complement numbers with the shift-and-add method needs a correction for the sign
bit and one addition per set bit of the multiplier. In 1950 Andrew Booth found a recoding that
handles *signed* operands uniformly and replaces a run of ones by a single subtraction at its bottom
and a single addition just past its top -- so \(0111\!\dots\!1\) costs two operations instead of many.
This report drives =datamunge='s =algorithms::booth_multiply=, verified against the built-in product
over hundreds of thousands of random signed pairs, and shows the recoding collapsing long runs of
ones into two operations.
#+end_abstract

* Recoding runs of ones

Booth scans the multiplier's bits from least to most significant, looking at each bit together with
the one below it (with an implicit \(0\) below the least bit). The pair \((b_i,b_{i-1})\) drives the
accumulator:

\[ (b_i,b_{i-1})=\begin{cases}
 0 & (0,0)\ \text{or}\ (1,1)\ \text{— inside a run, do nothing}\\
 -M\cdot 2^i & (0,1)\ \text{— start of a run of ones: subtract}\\
 +M\cdot 2^i & (1,0)\ \text{— end of a run of ones: add}
\end{cases} \]

The identity behind it is that a block of ones from bit \(j\) up to bit \(k\) equals
\(2^{k+1}-2^{j}\): rather than add \(M\) at every position in the block, subtract \(M2^{j}\) once when
entering it and add \(M2^{k+1}\) once when leaving. Because the same rule treats the multiplier's
top bit as a negative weight, the method multiplies *signed* two's-complement values with no special
sign handling -- the accumulator ends holding the exact signed product.

* Algorithm

#+begin_example
BOOTH(M, Q):                       # M = multiplicand, Q = multiplier
  acc = 0;  prev = 0               # prev is the implicit b_{-1}
  for i = 0 .. wordbits-1:
      cur = bit i of Q
      if (prev, cur) == (1, 0): acc += M << i     # leaving a run of ones
      if (prev, cur) == (0, 1): acc -= M << i     # entering a run of ones
      prev = cur
  return acc                       # exact signed product
#+end_example

* Worked example: signed products and the run-collapsing effect

We check a few signed products against the built-in operator, then count how many add/subtract steps
Booth performs across multipliers with growing runs of ones, comparing to the number of one-bits a
plain shift-and-add would need.

#+name: bo-run
#+begin_src c++ :eval no
    std::cout << "=== Booth's signed multiplication ===\n";
    for (auto [x, y] : std::vector<std::pair<int, int>>{{-7, 6}, {123456, -789}, {-1000, -1000}, {32767, 32767}}) {
        const auto r = booth_multiply(x, y);
        std::cout << x << " * " << y << " = " << r.product << "  (built-in "
                  << static_cast<long long>(x) * y << "; " << r.additions << " adds, "
                  << r.subtractions << " subs)\n";
    }
    std::cout << "\nmultiplier = 2^k - 1 (a run of k ones): Booth uses exactly 2 operations\n";
    std::vector<double> kx, boothops, naive;
    for (int k = 1; k <= 16; ++k) {
        const int    q = (1 << k) - 1; // k ones
        const auto   r = booth_multiply(1, q);
        const int    ops = r.additions + r.subtractions;
        kx.push_back(k); boothops.push_back(ops); naive.push_back(k); // naive = popcount = k
        if (k <= 4 || k == 16)
            std::printf("q=2^%d-1 (%d ones): Booth ops=%d, shift-add ops=%d\n", k, k, ops, k);
    }

    auto plot = RPlot::create();
    plot.line(kx, naive, "n", RGB{220, 38, 38}, 2.0);
    plot.points(kx, naive, "n", RGB{220, 38, 38}, 5.0);
    plot.line(kx, boothops, "b", RGB{5, 150, 105}, 2.0);
    plot.points(kx, boothops, "b", RGB{5, 150, 105}, 5.0);
    plot.legend({"shift-add: one op per 1-bit", "Booth: 2 ops per run of 1s"},
                {{220, 38, 38}, {5, 150, 105}});
    plot.title("Booth collapses a run of k ones into two operations")
        .x_label("length k of the run of ones").y_label("add/subtract operations").background({250, 250, 252});
    plot.save_svg("build/org/booth.svg");
    std::cout << "\nwrote booth.svg\n";
#+end_src

Every signed product matches the built-in operator, including the negative-times-negative and
near-overflow corners -- Booth's recoding needs no separate sign logic. The operation counts show the
payoff: a multiplier that is a solid run of \(k\) ones costs a plain shift-and-add \(k\) additions but
costs Booth exactly *two* operations, one subtract entering the run and one add leaving it.

The red shift-add line climbs with the run length while the green Booth line stays pinned at two. Real
multipliers are a mix of runs and isolated bits, so the saving is smaller in practice -- but the same
recoding, in its radix-4 (modified Booth) form, is what lets hardware multipliers halve the number of
partial products they must sum.
