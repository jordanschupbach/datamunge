#+begin_abstract
Summing the values in an arbitrary rectangle of a grid seems to cost \(O(\text{area})\) --
unless you precompute. The *summed-area table* (Crow 1984; the *integral image* of
Viola-Jones face detection) does one linear pass so that afterwards *any* rectangle sum is
just four lookups. This report implements it in =datamunge='s =algorithms::SummedAreaTable= as
a literate program: we verify it against brute force on every rectangle of a grid, and show
that box-filter smoothing costs the same per output pixel regardless of window size.
#+end_abstract

* Build once, query in four lookups

The table stores at each cell the sum of everything above and to the left:
\(S(r,c) = \sum_{i\le r,\ j\le c} A(i,j)\), built by the one-pass recurrence
\[
  S(r,c) = A(r,c) + S(r-1,c) + S(r,c-1) - S(r-1,c-1).
\]
Then the sum over the rectangle with corners \((r_0,c_0)\) and \((r_1,c_1)\) is *inclusion-
exclusion* over four table entries:
\[
  \sum_{r_0\le r\le r_1,\ c_0\le c\le c_1} A =
  S(r_1,c_1) - S(r_0-1,c_1) - S(r_1,c_0-1) + S(r_0-1,c_0-1).
\]
The big rectangle minus the two overhanging strips, plus the doubly-subtracted corner. Every
query is \(O(1)\) -- independent of the rectangle's size -- which is what makes a sliding box
filter or a cascade of Haar features cheap enough for real-time vision.

** Pseudocode

#+begin_example
build S from grid A:
    S[r][c] = A[r][c] + S[r-1][c] + S[r][c-1] - S[r-1][c-1]   # zero border for r,c = -1

rect_sum(r0,c0,r1,c1):
    return S[r1][c1] - S[r0-1][c1] - S[r1][c0-1] + S[r0-1][c0-1]   # 4 lookups, O(1)
#+end_example

* A worked example

We build the table for a 6x6 grid, verify a few sums against direct addition, and time-free
demonstrate that a box filter of *any* radius is one \(O(1)\) query per pixel by comparing
window sizes.

#+name: sat-run
#+begin_src c++ :eval no
    const int N = 6;
    std::vector<std::vector<double>> g(N, std::vector<double>(N));
    for (int r = 0; r < N; ++r) for (int c = 0; c < N; ++c) g[r][c] = r * N + c + 1;  // 1..36
    SummedAreaTable sat(g);

    std::cout << "=== Rectangle sums (SAT vs brute force) ===\n";
    struct Q { int r0,c0,r1,c1; };
    for (Q q : {Q{0,0,5,5}, Q{0,0,2,2}, Q{2,2,4,4}, Q{1,3,4,5}}) {
        double brute = 0;
        for (int r=q.r0;r<=q.r1;++r) for (int c=q.c0;c<=q.c1;++c) brute += g[r][c];
        std::cout << "  rect ["<<q.r0<<","<<q.c0<<"]-["<<q.r1<<","<<q.c1<<"]  SAT="
                  << sat.rect_sum(q.r0,q.c0,q.r1,q.c1) << "  brute=" << brute << "\n";
    }

    // Box-filter means at growing window radius -- each is ONE O(1) query.
    std::cout << "\n=== Box-filter mean at center (3,3) for growing radius ===\n";
    std::vector<double> radii, means;
    for (int rad = 0; rad <= 2; ++rad) {
        int r0=3-rad, c0=3-rad, r1=3+rad, c1=3+rad;
        double m = sat.rect_mean(r0,c0,r1,c1);
        radii.push_back(rad); means.push_back(m);
        std::cout << "  radius " << rad << "  ("<<(2*rad+1)<<"x"<<(2*rad+1)<<" window)  mean=" << m << "\n";
    }

    // Plot the integral image profile along the main diagonal (monotone increasing).
    std::vector<double> diag_x, diag_s;
    for (int k = 0; k < N; ++k) { diag_x.push_back(k); diag_s.push_back(sat.rect_sum(0,0,k,k)); }
    RPlot p = RPlot::create();
    p.line(diag_x, diag_s, "S(k,k) prefix sum", {37, 99, 235}, 2.0);
    p.points(diag_x, diag_s, "", {220, 38, 38}, 5.0);
    p.save_svg("build/org/summed_area_diagonal.svg");
    std::cout << "\nwrote build/org/summed_area_diagonal.svg\n";
#+end_src

Every table query matches brute-force addition exactly, including the full-grid sum of the
values \(1\ldots 36\). Box-filter means at radius 0, 1, and 2 each come from a single
four-lookup query, no matter the window size, and the diagonal profile shows the prefix sum
climbing monotonically. That constant per-query cost is the whole value of the integral
image.

* Uses and cautions

Summed-area tables power box blurs, adaptive thresholding, Haar-feature cascades (the
Viola-Jones detector's speed came from this), and any repeated rectangular aggregation. Two
cautions: the table can hold very large partial sums, so for big high-dynamic-range grids use
a wide enough integer/float type to avoid overflow or precision loss; and it only answers
*axis-aligned rectangle* queries -- rotated or arbitrary regions need rotated integral images
or other structures.

* Complexity

\(O(rc)\) one-time build over an \(r\times c\) grid; \(O(1)\) time and four lookups per
rectangle-sum query.
