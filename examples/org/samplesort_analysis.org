#+begin_abstract
Quicksort splits around one pivot; *samplesort* splits around many. It draws a sample from the data,
sorts it to obtain \(k-1\) *splitters*, distributes every element into one of \(k\) buckets by those
splitters, and sorts the buckets. With \(k\) chosen for the memory hierarchy or the number of
processors, samplesort is the method of choice for *parallel* and *external* sorting, where balanced
buckets matter more than a tight comparison count. This report drives =datamunge='s
=algorithms::samplesort=, verified against =std::sort= over thousands of random and adversarial
arrays, and shows the balanced buckets good splitters produce.
#+end_abstract

* Splitters cut the data into balanced pieces

Choose a bucket count \(k\). *Oversample*: pick \(k\cdot s\) elements (here \(s=3\)), sort them, and
take every \(s\)-th as a splitter, yielding sorted splitters \(x_1<\dots<x_{k-1}\). Oversampling makes
the splitters close to the true quantiles, so the buckets come out nearly equal in size even on skewed
data -- the crucial property for load balance. Every element \(v\) is placed in bucket

\[ b(v)=\big|\{\,i : x_i\le v\,\}\big|\in\{0,\dots,k-1\}, \]

found by a binary search over the splitters. The buckets are then sorted independently -- recursively
by samplesort, or by a base-case sort for small ones -- and concatenated. Because bucket \(i\) holds
exactly the values in \((x_{i-1},x_i]\), no merge is needed: sorting the buckets and reading them in
order sorts the whole array. The one hazard is a heavily duplicated key, which can pile into a single
bucket; detecting that a bucket did not shrink and sorting it directly keeps the recursion finite.

* Algorithm

#+begin_example
SAMPLESORT(a):
  if small: base-case sort
  sample k*s elements; sort; take every s-th as splitters x_1..x_{k-1}
  for each element v: place v in bucket b(v) = #{ x_i <= v }
  recursively samplesort each bucket; concatenate
#+end_example

* Worked example: sorting, and bucket balance

We sort a scrambled array, then classify a large random sample into buckets and plot the bucket sizes,
which oversampled splitters keep close to equal.

#+name: sp-run
#+begin_src c++ :eval no
    std::vector<int> a = {37, 12, 88, 4, 61, 25, 9, 73, 50, 18, 96, 42, 5, 67, 30};
    auto s = a; samplesort(s);
    std::cout << "=== samplesort ===\n";
    std::cout << "input:  "; for (int x : a) std::cout << x << " "; std::cout << "\n";
    std::cout << "sorted: "; for (int x : s) std::cout << x << " "; std::cout << "\n\n";

    // Bucket sizes for a large random sample with k = 8 buckets.
    std::mt19937_64 rng(21);
    const int n = 8000, k = 8, os = 3;
    std::vector<int> data(n); for (auto& x : data) x = (int)(rng() % 1000000);
    std::vector<int> sample; for (int i = 1; i <= k * os; ++i) sample.push_back(data[(long long)i * n / (k * os + 1)]);
    std::sort(sample.begin(), sample.end());
    std::vector<int> spl; for (int i = 1; i < k; ++i) spl.push_back(sample[i * os]);
    std::vector<int> sizes(k, 0);
    for (int v : data) sizes[std::upper_bound(spl.begin(), spl.end(), v) - spl.begin()]++;
    std::vector<double> heights; std::vector<std::string> labels;
    std::cout << "bucket sizes (n=" << n << ", k=" << k << "):\n";
    for (int i = 0; i < k; ++i) { std::cout << "  bucket " << i << ": " << sizes[i] << "\n"; heights.push_back(sizes[i]); labels.push_back("B" + std::to_string(i)); }

    auto plot = RPlot::barplot(heights, labels, "size", RGB{37, 99, 235});
    plot.abline_h((double)n / k, RGB{220, 38, 38}, 1.5);
    plot.title("Samplesort buckets are near-balanced (red line = n/k ideal)")
        .x_label("bucket").y_label("elements").background({250, 250, 252});
    plot.save_svg("build/org/samplesort.svg");
    std::cout << "\nwrote samplesort.svg\n";
#+end_src

Samplesort sorts correctly -- matching =std::sort= across thousands of random and adversarial arrays --
and the bucket sizes stay within a small factor of the ideal \(n/k\), with no bucket dominating.
Heavier oversampling tightens the balance further; even this light sample avoids the catastrophic
skew a single random pivot can suffer. That reasonable balance is what a parallel or external sort
needs: every processor or disk block gets a comparable share of the work.

The bars scatter around the red \(n/k\) line but none runs away: oversampled splitters approximate the
true quantiles well enough that every bucket gets a workable share. That is samplesort's reason for
being -- not a lower comparison count than quicksort, but the *balanced-enough partition* that lets the
work be spread across cores, machines, or passes over disk without one piece becoming the bottleneck.
