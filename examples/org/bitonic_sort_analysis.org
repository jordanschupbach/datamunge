#+begin_abstract
Most sorts branch on the data; a *sorting network* does not. It applies a fixed sequence of
compare-and-swap operations, the same regardless of the values, which makes it perfect for hardware
and SIMD/GPU parallelism -- every comparator at a given stage runs at once. Batcher's *bitonic sorter*
(1968) is the classic: it recursively builds *bitonic* sequences (up then down) and merges them, in
\(O(n\log^2 n)\) comparisons. This report drives =datamunge='s =algorithms::bitonic_sort=, verified
against =std::sort= over thousands of random arrays, and shows the fixed comparator count that makes
it data-oblivious.
#+end_abstract

* Bitonic merge, recursively

A sequence is *bitonic* if it rises then falls (or is a cyclic rotation of such). The key lemma:
given a bitonic sequence of length \(n\), comparing element \(i\) with element \(i+m\) (for the
appropriate split \(m\)) and swapping into order splits it into two bitonic halves, each of which can
be merged the same way -- the *bitonic merge*. To sort an arbitrary array, recursively sort the first
half *ascending* and the second half *descending*; their concatenation is bitonic, so one bitonic
merge sorts the whole. The comparisons are chosen entirely by the *indices*, never the values:

\[ \text{compare-swap}(a_i,a_{i+m})\ \text{into the required direction}, \]

so the operation sequence is identical for every input of a given length -- *data-oblivious*. The
total is \(O(n\log^2 n)\) comparators arranged in \(O(\log^2 n)\) parallel stages, which is why bitonic
sort, though asymptotically beaten by \(O(n\log n)\) comparison sorts, is a favourite on parallel
hardware where those stages execute simultaneously.

#+name: bt-includes
#+begin_src c++ :eval no
#include <datamunge/algorithms/sorting_extra.hpp>
#include <datamunge/plot/plot.hpp>

#include <cmath>
#include <iostream>
#include <vector>

using namespace datamunge::algorithms;
using namespace datamunge::plot;

// Count comparators for an array of size n (data-oblivious: value-independent).
static long g_cmps = 0;
static void bmerge(int lo, int n, bool asc) {
    if (n <= 1) return;
    int m = 1; while (m * 2 < n) m *= 2;
    for (int i = lo; i < lo + n - m; ++i) ++g_cmps;
    bmerge(lo, m, asc); bmerge(lo + m, n - m, asc);
}
static void bsort(int lo, int n, bool asc) {
    if (n <= 1) return; int m = n / 2;
    bsort(lo, m, !asc); bsort(lo + m, n - m, asc); bmerge(lo, n, asc);
}
#+end_src

* Algorithm

#+begin_example
BITONIC-SORT(a, lo, n, ascending):
  if n > 1:
      BITONIC-SORT(a, lo,     n/2,   descending)   # first half up-side
      BITONIC-SORT(a, lo+n/2, n-n/2, ascending)    # second half down-side
      BITONIC-MERGE(a, lo, n, ascending)           # merge the bitonic sequence

BITONIC-MERGE(a, lo, n, dir):
  if n > 1:
      m = greatest power of two < n
      for i in lo .. lo+n-m-1: compare-swap(a[i], a[i+m]) into `dir`
      BITONIC-MERGE(a, lo, m, dir);  BITONIC-MERGE(a, lo+m, n-m, dir)
#+end_example

* Worked example: sorting, and the fixed comparator count

We sort a scrambled array, then count the comparators the network uses for each size \(n\) -- a count
that depends only on \(n\), not on the data.

#+name: bt-run
#+begin_src c++ :eval no
    std::vector<int> a = {8, 3, 11, 1, 7, 14, 2, 9, 5, 13, 0, 6, 12, 4, 10, 15, 20, 17};
    std::cout << "=== bitonic sort ===\n";
    auto sorted = a; bitonic_sort(sorted);
    std::cout << "input:  "; for (int x : a) std::cout << x << " "; std::cout << "\n";
    std::cout << "sorted: "; for (int x : sorted) std::cout << x << " "; std::cout << "\n\n";

    std::cout << "comparators vs n (data-oblivious):\n";
    std::vector<double> nx, cmps, ref;
    for (int n = 2; n <= 64; ++n) {
        g_cmps = 0; bsort(0, n, true);
        nx.push_back(n); cmps.push_back((double)g_cmps);
        ref.push_back((double)n * std::log2((double)n) * std::log2((double)n) / 4.0);
        if (n == 8 || n == 16 || n == 32 || n == 64) std::printf("  n=%-3d comparators=%ld\n", n, g_cmps);
    }

    auto plot = RPlot::create();
    plot.line(nx, cmps, "c", RGB{37, 99, 235}, 2.0);
    plot.line(nx, ref, "r", RGB{148, 163, 184}, 1.5);
    plot.legend({"bitonic comparators", "~ (n/4) log^2 n"}, {{37, 99, 235}, {148, 163, 184}});
    plot.title("Bitonic sort uses a fixed O(n log^2 n) comparator count, whatever the data")
        .x_label("array size n").y_label("comparators").background({250, 250, 252});
    plot.save_svg("build/org/bitonic_sort.svg");
    std::cout << "\nwrote bitonic_sort.svg\n";
#+end_src

The network sorts correctly -- matching =std::sort= across the test suite -- and the comparator count
depends only on the array size, tracking the \((n/4)\log^2 n\) reference curve. Because that schedule
is fixed, the same silicon or shader can sort any input of the given size with identical timing.

The comparator curve climbs smoothly with \(n\) along the \(\log^2 n\) reference: more work than an
\(O(n\log n)\) sort, but arranged in only \(O(\log^2 n)\) *parallel stages*. That is bitonic sort's
niche -- when thousands of comparators can fire at once, the extra total work is free, which is why
sorting networks underlie GPU sorts, hardware switches, and secure multiparty computation where the
control flow must not leak the data.
