#+begin_abstract
Timsort is the sort in your standard library: Python's =sorted=, Java's =Arrays.sort= for objects, and
more all use Tim Peters's 2002 algorithm. Its insight is that real data is rarely random -- it comes
in already-ordered *runs* -- so Timsort finds those runs, extends short ones with insertion sort, and
merges them with a carefully balanced stack discipline, for guaranteed \(O(n\log n)\) worst case and
*linear* time on already-sorted input. This report drives =datamunge='s =algorithms::timsort=,
verified against =std::sort= over thousands of random and run-structured arrays, and shows its
adaptivity.
#+end_abstract

* Runs, minrun, and the merge invariants

Timsort scans left to right for a *natural run*: a maximal ascending stretch, or a strictly descending
one (which it reverses in place). If a run is shorter than a computed *minrun* (32-64, chosen so the
number of runs is near a power of two), it is extended to =minrun= elements with *binary insertion
sort* -- cheap because most of the run is already ordered. Each run is pushed onto a stack, and after
every push Timsort *merges* to keep the run lengths satisfying two invariants (for the top three
lengths \(X,Y,Z\)):

\[ X>Y+Z \qquad\text{and}\qquad Y>Z. \]

These invariants keep the pending runs balanced -- roughly geometrically decreasing -- so merges
combine similarly sized runs and the total merge cost stays \(O(n\log n)\). When they are violated the
offending runs are merged immediately (choosing which of the two adjacent merges keeps the stack
healthy). Merging two adjacent ascending runs is a stable two-way merge through a temporary buffer.
Because a fully sorted array is a single run of length \(n\), Timsort finishes it in one pass -- linear
time -- while random data still costs the merge-sort optimum. (Production Timsort adds *galloping* mode
to speed merges of very unbalanced data; we omit that constant-factor refinement.)

#+name: ts-includes
#+begin_src c++ :eval no
#include <datamunge/algorithms/sorting_hybrid.hpp>
#include <datamunge/plot/plot.hpp>

#include <algorithm>
#include <iostream>
#include <random>
#include <vector>

using namespace datamunge::algorithms;
using namespace datamunge::plot;

// Count the natural runs (ascending or descending) in a sequence.
static int count_runs(const std::vector<int>& a) {
    if (a.size() < 2) return (int)a.size();
    int runs = 0; int i = 1;
    while (i < (int)a.size()) {
        bool asc = a[i] >= a[i - 1]; ++i;
        while (i < (int)a.size() && (a[i] >= a[i - 1]) == asc) ++i;
        ++runs;
    }
    return runs;
}
#+end_src

* Algorithm

#+begin_example
TIMSORT(a):
  minrun = compute from n
  while more input:
      find the next natural run (reverse it if descending)
      if run shorter than minrun: extend to minrun via binary insertion sort
      push run on the stack; MERGE-COLLAPSE (restore the size invariants)
  merge the remaining runs down to one
#+end_example

* Worked example: sorting, and adaptivity to runs

We sort a scrambled array, then count how many natural runs the input contains as it goes from sorted
to fully shuffled -- fewer runs mean fewer, cheaper merges.

#+name: ts-run
#+begin_src c++ :eval no
    std::vector<int> a = {5, 6, 7, 1, 2, 3, 9, 8, 4, 0, 10, 11};
    auto s = a; timsort(s);
    std::cout << "=== timsort ===\n";
    std::cout << "input:  "; for (int x : a) std::cout << x << " "; std::cout << "\n";
    std::cout << "sorted: "; for (int x : s) std::cout << x << " "; std::cout << "\n";
    std::cout << "natural runs in input: " << count_runs(a) << "\n\n";

    std::mt19937_64 rng(9);
    const int n = 1000;
    std::vector<int> base(n); for (int i = 0; i < n; ++i) base[i] = i;
    std::vector<double> frac, runs;
    std::cout << "shuffled fraction   natural runs\n";
    for (int pct = 0; pct <= 100; pct += 10) {
        std::vector<int> v = base;
        std::shuffle(v.begin(), v.begin() + n * pct / 100, rng);
        frac.push_back(pct / 100.0); runs.push_back(count_runs(v));
        if (pct % 20 == 0) std::printf("  %3d%%              %d\n", pct, count_runs(v));
    }

    auto plot = RPlot::create();
    plot.line(frac, runs, "r", RGB{37, 99, 235}, 2.0);
    plot.points(frac, runs, "r", RGB{37, 99, 235}, 6.0);
    plot.legend({"natural runs"}, {{37, 99, 235}});
    plot.title("Timsort is adaptive: ordered input has few runs, so few merges")
        .x_label("fraction of the array shuffled").y_label("natural runs").background({250, 250, 252});
    plot.save_svg("build/org/timsort.svg");
    std::cout << "\nwrote timsort.svg\n";
#+end_src

Timsort sorts correctly -- matching =std::sort= across thousands of random and run-structured arrays --
and the run count tells the adaptivity story: a sorted array is a single run merged in linear time,
while a shuffled one shatters into many short runs that cost the usual \(O(n\log n)\).

The natural-run count climbs steeply with disorder: order in the input is exactly what Timsort turns
into speed, since each existing run is one it never has to create. That real-world adaptivity -- linear
on sorted or reverse-sorted data, optimal on random -- plus stability is why Timsort, not a textbook
quicksort, is the default sort of Python and Java.
