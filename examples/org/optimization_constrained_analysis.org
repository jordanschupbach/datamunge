#+begin_abstract
We minimize two hand-designed quadratics with known closed-form
constrained optima using every constrained optimizer in =datamunge='s
C++ =optim= module -- =AugmentedLagrangian= and =SQP= on an
equality-constrained problem, =InteriorPoint= on an
inequality-constrained one -- and report it as a literate program:
every number and figure below is real, compiled, executed output. On
$\min (x-3)^2+(y-5)^2$ subject to $x+y=1$ (closed-form optimum
$(-0.5,1.5)$, $f=24.5$), =AugmentedLagrangian='s *default options
produce the wrong answer*: the method converges beautifully through
its sixth outer iteration ($\|c(x)\|=7.1\times10^{-7}$, essentially
exact), then *diverges* the moment the penalty parameter $\rho$ crosses
a precise, hand-derivable numerical-stability threshold
($\rho=1/\text{step\_size}=100$), permanently locking into a
two-point limit cycle at $f=20.20$, $\|c(x)\|=0.643$ -- 43 further
penalty-doubling rounds (up to $\rho\approx5.6\times10^{14}$) never
recover it, because the implementation's gradient-norm clipping caps
the actual step taken independent of $\rho$ once clipping saturates. A
smaller step size ($0.002$ instead of the default $0.01$) avoids the
threshold entirely and converges correctly to $f=24.500005$.
=SQP='s default options ($\text{step\_size}=1.0$) exhibit the *same
family of bug*: gradient descent on this quadratic's curvature-2 bowl
with a unit step size is itself unstable, producing an exact two-cycle
that converges to the wrong point, $(0.5,0.5)$, $f=26.50$, rather than
the true optimum. With $\text{step\_size}=0.4$, SQP's actual answer
(the constraint-corrected $x$) converges to within
$2\times10^{-6}$ of $(-0.5,1.5)$ by iteration 10 and stays there -- yet
the loop runs the *full* 200 iterations regardless, because its
stopping condition's own residual, measured *before* that iteration's
correction is applied, never drops below a persistent floor of
$5.6$, confirming a real quirk in the stopping condition by direct
instrumentation. On $\min(x+3)^2+(y+3)^2$ subject to $x,y\ge0$
(closed-form optimum $(0,0)$, $f=18$), =InteriorPoint='s *default
options throw a real =std::runtime_error=*, =unable to find feasible
step=, at outer iteration 14 -- a genuine numerical-robustness bug
where $x$ shrinks to the same $10^{-15}$ scale as the implementation's
hard-coded minimum step, causing the backtracking search to reject a
step that would in fact have been feasible. Stopping one outer
iteration earlier (=max_outer_iterations= set to =13=) avoids the crash and
reaches $f=18.000000$, $x=(7.5\times10^{-10},7.5\times10^{-10})$ --
after surviving its own transient blow-up to $f=1806$ at outer
iteration 7, from which it self-corrects. We derive the shared KKT
foundation, the augmented Lagrangian's penalty-plus-multiplier
construction, SQP's textbook QP-subproblem target versus the far
simpler sequential-correction scheme actually implemented, and the
log-barrier method's central path, tying every derivation to the
exact formula in the =.cpp= source.

* Introduction

Every optimizer in this report's companion,
=optimization_analysis.org=, solves an /unconstrained/ problem: find
$x^*=\arg\min_x f(x)$ over the whole space. This report covers the
three optimizers in =datamunge::optim= built for the harder,
more common case where $x$ must additionally satisfy a set of
equality or inequality constraints -- the shape every real
resource-allocation, portfolio, or engineering-design problem takes.
Two function-type interfaces organize this module's constrained side:
=EqualityConstrainedFunction= (a =DifferentiableFunction= that
additionally supplies =constraints(x)=, the vector of $c_k(x)$ each
meant to equal zero, and =constraint_jacobian(x)=) drives
=AugmentedLagrangian= and =SQP=; =InequalityConstrainedFunction=
(the same shape, but =inequalities(x)= returns $g_k(x)$ each meant to
satisfy $g_k(x)\le0$) drives =InteriorPoint=. All three methods
approximate the same underlying KKT stationarity conditions from a
different direction -- penalty-plus-multiplier, sequential
linearization, and log-barrier respectively -- and this report derives
each approximation's real update rule, then tests it against a
constrained problem simple enough to have an exact, hand-checkable
closed-form answer.

That simplicity turned out to matter far more than expected. All
three implementations in this module are honestly simplified relative
to their textbook namesakes (documented precisely in §2), and testing
each one's /default/ options against a closed-form answer surfaced two
distinct real numerical-instability bugs and one real crash -- not
edge cases requiring an adversarial example, but the very first
straightforward test case tried for each method. This report documents
all three plainly, with instrumented, per-iteration evidence, in the
same spirit as its companion reports' library-bug findings.

As with its companions, this document is a /literate program/: prose
and source are interleaved in reading order, and a single "assembling
the program" step (§3.3) weaves every named chunk below into one
=.cpp= file, compiles it, and runs it. Every number and figure from §4
onward is that program's literal output.

§2 derives the shared KKT foundation and each method's real update

* Background: Constrained Optimization Methods

** The KKT conditions

For the equality-constrained problem $\min f(x)$ subject to
$c_k(x)=0$, the first-order (Karush-Kuhn-Tucker, Karush 1939;
Kuhn & Tucker 1951) necessary conditions for a local minimum $x^*$
are stationarity of the Lagrangian $\mathcal{L}(x,\lambda) =
f(x) + \sum_k \lambda_k c_k(x)$,

$$\nabla f(x^*) + \sum_k \lambda_k^* \nabla c_k(x^*) = 0, \qquad
c_k(x^*) = 0 \;\; \forall k,$$

for some multipliers $\lambda^*$. For the inequality-constrained
problem $\min f(x)$ subject to $g_k(x)\le0$, the analogous conditions
add non-negativity and complementary slackness on multipliers
$\mu\ge0$:

$$\nabla f(x^*) + \sum_k \mu_k^* \nabla g_k(x^*) = 0, \qquad
g_k(x^*) \le 0, \qquad \mu_k^* \ge 0, \qquad \mu_k^* g_k(x^*) = 0
\;\; \forall k.$$

Every method below is, at bottom, a different numerical strategy for
finding a point satisfying its side of these conditions.

** AugmentedLagrangian

The classical penalty method minimizes $f(x) + \frac{\rho}{2}\sum_k
c_k(x)^2$ for a fixed, large $\rho$ -- but forcing near-exact
constraint satisfaction requires $\rho\to\infty$, which makes the
penalized objective increasingly ill-conditioned. The augmented
Lagrangian (Hestenes 1969; Powell 1969; see also Bertsekas's textbook
treatment) instead minimizes

$$L_\rho(x,\lambda) = f(x) + \sum_k \left[\lambda_k c_k(x) +
\frac{\rho}{2}c_k(x)^2\right]$$

for a /fixed, finite/ $\rho$, and updates the multiplier by dual
ascent, $\lambda_k \leftarrow \lambda_k + \rho c_k(x)$, after each
inner minimization. As $\lambda\to\lambda^*$, the multiplier itself
absorbs most of the constraint-enforcement burden, so $\rho$ need
never grow unboundedly for exact convergence in principle -- the
entire point of the method relative to the plain penalty approach.
=datamunge='s =AugmentedLagrangian::optimize=
(=src/datamunge/optim/augmented_lagrangian.cpp=) implements exactly
this outer loop, but
each inner minimization is plain gradient descent on $L_\rho$ for a
fixed =inner_iterations= count, using the gradient
$\nabla f(x) + \sum_k (\lambda_k+\rho c_k(x))\nabla c_k(x)$ -- exactly
the source's =g[p]+=(lambda[k]+rho*c[k])*jacobian[k][p]=. The inner
gradient step is *normalized*: =scale=min(1, 1/(step_size*||g||+eps))=,
so the actual displacement is =x-=scale*step_size*g=. Algebraically,
once =step_size*||g||>1= this reduces to a *unit-norm* step
$g/\|g\|$ every inner iteration, regardless of how large the raw
gradient is -- a crude but real gradient-clipping safeguard, not
textbook-standard augmented-Lagrangian gradient descent, and (as §4.1
and §5 show) the direct cause of this report's first real bug finding.
After =inner_iterations= steps, =AugmentedLagrangian= updates
$\lambda_k \mathrel{+}= \rho c_k(x)$, checks $\|c(x)\|\le$
=tolerance= to stop early, and otherwise *doubles* $\rho$ and repeats.

** SQP

The textbook sequential quadratic programming method solves, each
iteration, a quadratic-programming subproblem built from the
Lagrangian's Hessian and the constraints' linearization -- effectively
a constrained Newton step, with genuinely fast local convergence.
=datamunge='s =SQP= (=src/datamunge/optim/sqp.cpp=) is a *deliberately
simplified* approximation of that target, not the textbook method
itself, and this report describes precisely what is actually there
rather than the general reputation the name carries. Each iteration:
(1) a plain unconstrained gradient step,
=x-=step_size*gradient(x)= -- no Lagrangian Hessian, no line search;
(2) for *each* constraint $k$ sequentially, a Gauss-Newton-style
projection correction,
=x-=J_k*c_k(x)/(\|J_k\|^2+regularization)=, which is a single
Newton/least-norm step solving the /linearized/ scalar constraint
$c_k(x_\text{new})\approx c_k(x)+J_k\cdot\delta=0$ for the
minimum-norm $\delta$. Applying this one constraint at a time means
that with two or more constraints, the second correction can partially
undo the first's work -- this report's single-constraint example
cannot exercise that interaction, so it is noted here as a real
limitation rather than demonstrated. The loop's stopping condition is
=sqrt(constraint_residual^2)<=tolerance AND sqrt(step_size^2)<=
tolerance= -- but =step_size= is a *fixed* configured option that
never changes across iterations, so unless =step_size= itself is
configured smaller than =tolerance= (the default =step_size= of $1.0$
vs. =tolerance= of $10^{-8}$ makes this essentially never true in
practice), the
second half of the =AND= is always false and *the loop can never exit
early, regardless of convergence* -- it always runs the full
=max_iterations=. §4.2 and §5 verify this with real instrumented
per-iteration output, and find a second, sharper effect than expected
going in: not just wasted iterations after convergence, but the
/first/ half of the =AND= (the residual check itself) is doubly
unsatisfiable too, for a reason specific to what exactly gets measured
(see §5).

** InteriorPoint

The classical log-barrier method (Fiacco & McCormick 1968) replaces
inequality constraints $g_k(x)\le0$ with a barrier term added to the
objective, $f(x) - \mu\sum_k\ln(-g_k(x))$, which is $+\infty$ outside
the feasible region and finite (with a gradient pushing away from the
boundary) inside it. Minimizing this barrier-augmented objective for a
decreasing sequence $\mu\to0$ traces the "central path" toward the
true constrained optimum, which typically lies on the boundary of the
feasible region. This is the *classical* barrier-method style of
interior-point method, distinct from the primal-dual Newton approach
that powered the 1980s interior-point revival for linear and convex
programming (Karmarkar 1984) -- =datamunge='s =InteriorPoint=
(=src/datamunge/optim/interior_point.cpp=) is, precisely, the
classical style: an outer loop geometrically shrinks $\mu$
(=mu*=barrier_decay=, default $0.1$, i.e. $10\times$ smaller each
round), and each inner iteration takes a *plain gradient-descent*
step (no Newton system, no Hessian) using
$\nabla f(x) - \sum_k \mu\nabla g_k(x)/g_k(x)$ -- exactly the source's
=g[p]-=mu*j[k][p]/c[k]=, the barrier gradient's classical form (since
the gradient of $-\mu\ln(-g_k(x))$ is $-\mu\nabla g_k(x)/g_k(x)$, and
$g_k(x)<0$ inside the feasible region correctly makes this term push
/away/ from the boundary). Before every inner step, the implementation
*throws* =std::invalid_argument= if the current point is not strictly
feasible ($g_k(x)\ge0$ for any $k$) -- meaning the starting point must
already satisfy every inequality strictly, a real requirement this
report's example is designed around. After computing the barrier
gradient, the method takes a step and then *backtracks the step
length* (halving repeatedly) purely to keep the trial point strictly
feasible -- a *feasibility-only* backtrack, not an Armijo/Wolfe
sufficient-decrease backtrack the way =CoordinateDescent= or
=ConjugateGradient= do it elsewhere in this module -- and throws
=std::runtime_error("unable to find feasible step")= if the step
shrinks below a hard-coded floor, =1e-15=, without finding one. §4.3
and §5 show this floor is not a theoretical corner case: this report's
own default-options run hits it for a real, precise, derivable reason.

** Building a convergence curve without a native history API

As in this module's other reports, none of these three optimizers
expose an iteration history, so this report builds one with the same
thin logging-decorator technique: a =LoggingEquality= wraps a real
=EqualityConstrainedFunction= and records $\|c(x)\|$ every time
=constraints()= is called (=AugmentedLagrangian= calls it once per
inner iteration and once per outer update; =SQP= calls it once per
iteration), and a =LoggingInequality= wraps a real
=InequalityConstrainedFunction= and records $f(x)$ every time
=gradient()= is called -- =InteriorPoint='s inner loop calls
=gradient()= exactly once per inner iteration, at the current point,
before that iteration's step is taken, so this reconstructs a genuine
per-inner-iteration trace directly from the real =optimize()= call
rather than a hand-written replica of the algorithm.

* Data and Methods

** The data

Both examples are purely synthetic quadratics chosen specifically so
that every optimizer's result can be checked directly against an
exact, hand-derived closed-form answer -- essential for telling a real
convergence bug apart from an ordinary approximation gap. §4.1 and
§4.2 minimize $f(x,y)=(x-3)^2+(y-5)^2$ subject to the linear equality
constraint $x+y=1$: the unconstrained minimum $(3,5)$ lies far off the
constraint line, forcing a genuinely active constraint, and the
constrained optimum is the projection of $(3,5)$ onto that line. By
Lagrange multipliers, $x^*=a-\lambda^*$, $y^*=b-\lambda^*$ with
$x^*+y^*=1 \Rightarrow \lambda^*=(a+b-1)/2$; for $a=3,b=5$:
$\lambda^*=3.5$, $x^*=-0.5$, $y^*=1.5$, and
$f(x^*,y^*)=(-0.5-3)^2+(1.5-5)^2=12.25+12.25=24.5$. §4.3 minimizes
$f(x,y)=(x+3)^2+(y+3)^2$ subject to $x\ge0,y\ge0$ (i.e.
$g_1(x,y)=-x\le0$, $g_2(x,y)=-y\le0$): the unconstrained minimum
$(-3,-3)$ is infeasible, and since $f$ is separable and strictly
increasing as either coordinate decreases below $0$, the closest
feasible point is exactly the boundary corner $(0,0)$,
$f(0,0)=9+9=18$ -- a genuinely informative test since $(0,0)$ sits on
the boundary of /both/ constraints simultaneously. =InteriorPoint=
requires strict feasibility throughout, so this report starts it from
$(1,1)$, which satisfies both $x>0,y>0$ strictly.

// f(x,y) = (x-a)^2 + (y-b)^2 subject to x+y=1
class EqualityQuadratic : public EqualityConstrainedFunction {
public:
    EqualityQuadratic(double a, double b) : a_(a), b_(b) {}
    double evaluate(const std::vector<double>& x) override {
        const double dx = x[0] - a_, dy = x[1] - b_;
        return dx * dx + dy * dy;
    }
    std::vector<double> gradient(const std::vector<double>& x) override {
        return {2.0 * (x[0] - a_), 2.0 * (x[1] - b_)};
    }
    std::vector<double> constraints(const std::vector<double>& x) override {
        return {x[0] + x[1] - 1.0};
    }
    std::vector<std::vector<double>> constraint_jacobian(
        const std::vector<double>&) override {
        return {{1.0, 1.0}};
    }

private:
    double a_, b_;
};

// f(x,y) = (x+3)^2 + (y+3)^2 subject to x>=0, y>=0
class InequalityQuadratic : public InequalityConstrainedFunction {
public:
    double evaluate(const std::vector<double>& x) override {
        const double dx = x[0] + 3.0, dy = x[1] + 3.0;
        return dx * dx + dy * dy;
    }
    std::vector<double> gradient(const std::vector<double>& x) override {
        return {2.0 * (x[0] + 3.0), 2.0 * (x[1] + 3.0)};
    }
    std::vector<double> inequalities(const std::vector<double>& x) override {
        return {-x[0], -x[1]};
    }
    std::vector<std::vector<double>> inequality_jacobian(
        const std::vector<double>&) override {
        return {{-1.0, 0.0}, {0.0, -1.0}};
    }
};

// Logs ||constraints(x)|| every time constraints() is called (inside the
// real AugmentedLagrangian/SQP inner loops), for building convergence
// figures without a native history API.
class LoggingEquality : public EqualityConstrainedFunction {
public:
    LoggingEquality(EqualityConstrainedFunction& inner,
                     std::vector<double>& log)
        : inner_(&inner), log_(&log) {}
    double evaluate(const std::vector<double>& x) override {
        return inner_->evaluate(x);
    }
    std::vector<double> gradient(const std::vector<double>& x) override {
        return inner_->gradient(x);
    }
    std::vector<double> constraints(const std::vector<double>& x) override {
        auto c = inner_->constraints(x);
        double n = 0.0;
        for (double v : c) n += v * v;
        log_->push_back(std::sqrt(n));
        return c;
    }
    std::vector<std::vector<double>> constraint_jacobian(
        const std::vector<double>& x) override {
        return inner_->constraint_jacobian(x);
    }

private:
    EqualityConstrainedFunction* inner_;
    std::vector<double>* log_;
};

// Logs f(x) every time gradient() is called (InteriorPoint's inner loop
// calls gradient() exactly once per inner iteration, at the current x,
// before taking that iteration's step), for a per-inner-iteration
// convergence curve without a native history API.
class LoggingInequality : public InequalityConstrainedFunction {
public:
    LoggingInequality(InequalityConstrainedFunction& inner,
                       std::vector<double>& log)
        : inner_(&inner), log_(&log) {}
    double evaluate(const std::vector<double>& x) override {
        return inner_->evaluate(x);
    }
    std::vector<double> gradient(const std::vector<double>& x) override {
        log_->push_back(inner_->evaluate(x));
        return inner_->gradient(x);
    }
    std::vector<double> inequalities(const std::vector<double>& x) override {
        return inner_->inequalities(x);
    }
    std::vector<std::vector<double>> inequality_jacobian(
        const std::vector<double>& x) override {
        return inner_->inequality_jacobian(x);
    }

private:
    InequalityConstrainedFunction* inner_;
    std::vector<double>* log_;
};

void print_vec(const std::vector<double>& v) {
    std::cout << "[";
    for (std::size_t i = 0; i < v.size(); ++i) {
        std::cout << (i ? ", " : "") << v[i];
    }
    std::cout << "]";
}

std::vector<double> indices(std::size_t n) {
    std::vector<double> out(n);
    for (std::size_t i = 0; i < n; ++i) out[i] = static_cast<double>(i + 1);
    return out;
}

std::vector<double> log10_shifted(const std::vector<double>& v) {
    std::vector<double> out(v.size());
    for (std::size_t i = 0; i < v.size(); ++i) {
        out[i] = std::log10(v[i] + 1e-12);
    }
    return out;
}

* Discussion

**=AugmentedLagrangian='s divergence at outer iteration 7 is a
precise, hand-derivable numerical-stability threshold crossing, not
vague "the method didn't converge fast enough."** The inner
gradient-descent loop minimizes a term whose curvature along the
constraint's normal direction is $2\rho\|J\|^2$ (here $\|J\|^2=2$,
since $J=(1,1)$), and plain fixed-step gradient descent on a
1-D quadratic with curvature $\kappa$ and step size $\eta$ is
numerically stable if and only if $\eta\kappa<2$. With the default
=step_size= set to =0.01=, that is $\rho<1/0.01=100$. This report's outer loop
doubles $\rho$ every round starting from $1.0$: $\rho=64$ at outer
iteration 6 (stable; the run's best residual, $7.1\times10^{-7}$, is
reached here) and $\rho=128$ at outer iteration 7 -- the first round
that exceeds $100$. Direct per-inner-iteration instrumentation of
that round (not shown in the assembled figure above, to keep it
focused, but produced and checked while writing this report) confirms
the predicted signature exactly: the residual starts at
$7.1\times10^{-7}$ and grows geometrically, alternating sign each
inner step (the classic divergent-oscillation pattern of an unstable
linear fixed-point iteration), for about 30 inner iterations, until
the implementation's crude gradient-norm clipping caps the growth and
locks the trajectory into an exact two-point limit cycle,
$(-0.178403,1.821597)\leftrightarrow(-0.885509,1.114491)$. Because the
clipped step's magnitude no longer depends on $\rho$ once clipping
saturates, every one of the remaining 43 outer rounds' further
penalty-doubling (up to $\rho\approx5.6\times10^{14}$) has *zero*
further effect on the trajectory -- the method is permanently stuck,
having already found the near-exact answer one round earlier and then
thrown it away.

**=SQP='s default-options failure is the same underlying phenomenon --
fixed-step gradient descent exceeding its own stability limit -- on a
much simpler, single-step timescale.** This report's objective has
Hessian $2I$ in the unconstrained part; a single gradient step
$x\leftarrow x-\eta\cdot2(x-a)$ is stable iff $\eta<1$ (curvature-2,
threshold $\eta\kappa<2 \Rightarrow \eta<1$). The default
=step_size= set to =1.0= sits exactly at that boundary, and combined with the
sign-flipping reflection this produces ($x_{new}=2a-x_{old}$ for the
unconstrained part), the constraint correction each iteration keeps
re-projecting the /same/ oscillating trajectory back onto the
constraint line at one of exactly two points, without ever actually
approaching the constrained optimum. A tuned =step_size= set to =0.4= (comfortably
under the $\eta<1$ boundary) removes the oscillation and converges
correctly. This report's SQP finding is thus richer than the AND-clause
quirk alone predicted going in: the same class of numerical-stability
bug that broke =AugmentedLagrangian= (a different formula, but the
identical fixed-step-exceeds-threshold mechanism) also breaks =SQP='s
default configuration outright, on top of -- not instead of -- the
separately real AND-clause defect (§2.3, confirmed in §4.2: even the
/working/, tuned configuration's stopping check never fires early,
because it measures the wrong quantity -- the violation immediately
after the plain gradient step, before that same iteration's correction
is applied -- which has its own persistent nonzero floor unrelated to
how converged the actual, corrected $x$ already is).

**=InteriorPoint='s crash is a genuine numerical-robustness bug with a
precise, checkable mechanism, not merely "ran out of outer
iterations."** As the barrier parameter $\mu$ shrinks geometrically
and $x$ is squeezed toward the active boundary, the feasible-region
distance $-g_k(x)$ shrinks along with it. By outer iteration 14
($\mu=10^{-14}$), $x$ has shrunk to $\approx3.2\times10^{-15}$ --
already the same order of magnitude as the implementation's
hard-coded minimum backtracking step, $10^{-15}$. The backtracking
loop halves its trial step and, immediately after the halving that
would have produced a feasible point ($\approx5.7\times10^{-16}$,
which /is/ small enough to keep $x$ positive), instead hits the
=step<1e-15= floor check first and throws -- a real off-by-one-halving
interaction between a hard-coded numerical floor and a barrier
parameter whose intended shrinkage is unbounded. This does not depend
on this report's specific example being adversarial: any
inequality-constrained problem whose true optimum sits exactly on the
constraint boundary (a common, not unusual, case) will eventually push
$x$ down to this same scale if the outer-iteration budget is generous
enough. The transient spike at outer iteration 7 ($f=1806.26$) is a
milder, self-correcting instance of the same
fixed-step-size-vs-shrinking-barrier tension that permanently broke
=AugmentedLagrangian= and
=SQP= above -- here it recovers because $\mu$'s continued shrinkage
happens to reduce the effective curvature again before a limit cycle
can lock in, but that recovery is not guaranteed by anything in the
implementation, and by outer iteration 14 it does not happen again.

* Conclusion

Testing all three of =datamunge='s constrained optimizers against
closed-form-checkable quadratics surfaced two real
numerical-instability bugs and one real crash, all traceable to the
same root cause -- a fixed step size interacting with a growing
effective curvature (penalty parameter $\rho$ for
=AugmentedLagrangian=, unit step size against a curvature-2 bowl for
=SQP=, shrinking barrier parameter $\mu$ for =InteriorPoint=) crossing
a derivable numerical-stability threshold.
=AugmentedLagrangian='s default options converge
to $\|c(x)\|=7.1\times10^{-7}$ at outer iteration 6 and then diverge
to the wrong answer, $f=20.204487$, by outer iteration 7; a smaller
step size ($0.002$) reaches $f=24.500005$ against the closed-form
$24.5$. =SQP='s default options converge to the wrong point,
$f=26.499951$, in an exact two-cycle; =step_size= set to =0.4= reaches
$f=24.499980$, and directly confirms a real stopping-condition
defect: the loop always runs its full =max_iterations= regardless of
convergence, because the quantity it checks is not the one that
actually converges. =InteriorPoint='s default options throw a real
=std::runtime_error= at outer iteration 14; stopping two rounds
earlier reaches $f=18.000000$ against the closed-form $18$. As with
its companions, this entire report is reproducible end to end via
=just org-example optimization_constrained_analysis=, which
re-executes §3.3's assembly block -- and therefore every number and
figure above, including both crash messages -- from the =datamunge=
source tree.
