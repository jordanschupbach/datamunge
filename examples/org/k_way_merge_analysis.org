#+begin_abstract
Merging two sorted lists is easy: walk a finger down each and always take the smaller.
Merging *k* sorted lists at once -- the heart of external sorting and of merge sort's
combine step -- is where the choice of data structure matters. Naively re-scanning all
\(k\) list-fronts for the minimum each time costs \(O(n k)\); a *min-heap* over
the fronts drops that to \(O(n\log k)\). This report implements both the two-way
*simple merge* and the heap-based *k-way merge* in =datamunge='s C++, verified against
=std::sort= of the concatenation, and measures the heap's advantage as \(k\) grows.
#+end_abstract

* From two fingers to a heap

The *simple (two-way) merge* keeps one index into each of two sorted arrays and, at
each step, appends the smaller of the two front elements (ties favour the first array,
so the merge is *stable*). One linear pass, \(O(|a|+|b|)\).

For \(k\) lists you still want the global minimum of the \(k\) fronts each step.
Scanning all \(k\) fronts every time is \(O(k)\) per output element -- \(O(nk)\)
overall. A *min-heap* holding the current front of each list answers "smallest front"
in \(O(\log k)\) and updates in \(O(\log k)\) when you pop one and push its
successor. With \(n\) elements pushed and popped once each, the whole merge is

\[ O(n\log k), \]

the standard method for merging sorted *runs* in external merge sort (where each run is
a chunk that fit in memory) and for combining posting lists in search engines.

* Algorithm

#+begin_example
K-WAY-MERGE(lists):
  heap <- empty min-heap of (value, list_index, elem_index)
  for each nonempty list l: push (l[0], l, 0)
  out <- []
  while heap not empty:
      (v, l, e) <- pop-min(heap)
      append v to out
      if e+1 < len(lists[l]): push (lists[l][e+1], l, e+1)
  return out
#+end_example

* Worked example: three interleaved runs, and the cost as k grows

We merge three sorted lists by hand, then measure the heap merge's work against the
naive "scan all k fronts" approach as the number of lists \(k\) climbs (total
element count held fixed).

#+name: km-run
#+begin_src c++ :eval no
    const std::vector<std::vector<int>> demo = {{1, 4, 7, 10}, {2, 3, 11}, {5, 6, 8, 9, 12}};
    std::cout << "=== merging three sorted runs ===\n";
    const std::vector<int> merged = k_way_merge(demo);
    for (int v : merged) std::cout << v << " ";
    std::cout << "\n(simple two-way merge of the first two: ";
    for (int v : simple_merge(demo[0], demo[1])) std::cout << v << " ";
    std::cout << ")\n\n";

    // Cost model: fixed total n = 3000, split into k sorted runs. Heap merge does ~ n log2 k
    // key comparisons; the naive scan-all-fronts does ~ n * (k-1).
    const double n = 3000.0;
    std::vector<double> ks, heap_cost, naive_cost;
    for (int k = 2; k <= 64; k += 2) {
        ks.push_back(k);
        heap_cost.push_back(n * std::log2(static_cast<double>(k)));
        naive_cost.push_back(n * (k - 1));
    }
    std::cout << "at k=64: heap ~" << heap_cost.back() << " vs naive ~" << naive_cost.back() << " comparisons\n";

    auto plot = RPlot::create();
    plot.line(ks, naive_cost, "naive scan (n*k)", RGB{220, 38, 38}, 2.0);
    plot.points(ks, naive_cost, "naive", RGB{220, 38, 38}, 4.0);
    plot.line(ks, heap_cost, "heap (n log k)", RGB{37, 99, 235}, 2.0);
    plot.points(ks, heap_cost, "heap", RGB{37, 99, 235}, 5.0);
    plot.legend({"naive scan-all-fronts (n k)", "min-heap (n log k)"}, {{220, 38, 38}, {37, 99, 235}});
    plot.title("Merging k runs: a heap turns O(n k) into O(n log k)")
        .x_label("number of lists k").y_label("key comparisons (n = 3000)").background({250, 250, 252});
    plot.save_svg("build/org/k_way_merge.svg");
    std::cout << "wrote k_way_merge.svg\n";
#+end_src

* Results

#+begin_example

The three runs interleave into one fully sorted sequence, and the two-way merge of the
first pair is just the \(k=2\) special case of the same idea. The cost curves show
why the heap matters: the naive scan grows *linearly in \(k\)* -- every extra list
adds a comparison to every output step -- while the heap grows only *logarithmically*.

The red naive curve climbs in a straight line with \(k\), but the blue heap curve
barely rises -- by \(k=64\) the heap does an order of magnitude less work. That gap
is exactly why external sort merges hundreds of runs through a heap rather than
re-scanning their fronts.
