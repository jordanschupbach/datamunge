    Fibonacci Search: Actual Schedules, Reads and Fallbacks

    Abstract

    Find an integer in a nondecreasing array and report its position or absence. Fibonacci search narrows its schedule with consecutive Fibonacci sizes rather than computing midpoint divisions. We begin with two actual reads on seven values, retain the original ten-value array and five queries, and inspect the native solver's pre/post states. The report-local retracing loop is replaced by same-pass owned records. Repeated clamped positions, an equality fallback, duplicates and a full query census distinguish reads from unique positions, primitive comparisons and elapsed time. A pure native schedule API checks very large hypothetical lengths without allocating corresponding arrays.

    Two actual reads find nine

    In [1,3,5,7,9,11,13], the smallest covering Fibonacci size is eight. Its predecessors are five and three. The native implementation starts with offset−1, probes offset+small=2 and reads five. Since five is below nine, it moves the offset to two and reduces the schedule from(3,5,8) to(2,3,5). The next probe is index four, whose value nine matches. There are two reads, three primitive key comparisons and one nonmatching schedule transition.

    The native schedule and its shrinking invariant

    For positive n, grow(small,middle,large) from(0,1,1) until large≥n, maintaining small+middle=large. The current offset is initially−1. During the main loop, probe min(offset+small,n−1). A read value below the key moves the offset to that index and updates the sizes as (new small,new middle,new large)=(old middle−old small,old small,old middle). A value above the key keeps the offset and sets (new small,new middle,new large)=(2old small−old middle,old middle−old small,old small). The implementation uses successive nonnegative differences, avoiding the unnecessary doubled intermediate in that second expression.

    Nondecreasing order justifies discarding the corresponding values. Each nonmatching main iteration decreases the Fibonacci rank by at least one. When large≤1, a possible remaining offset+1 position is checked by equality. That final check is a real read even when a previous read visited the same position. Covering-rank growth and search each take O(log(n+1)) word work. The schedule-addition count plus two is a conservative read bound, not an exact count or a claim of optimal comparisons.

    There is no midpoint division in this schedule. That arithmetic property alone does not imply faster execution than binary search on current hardware. Index checks, branches, key comparisons, memory access and preprocessing all matter. Fibonacci search here is exact membership in an already sorted array, distinct from unimodal numerical optimization.

    Repeated clamps, the equality fallback and duplicates

    The native implementation intentionally retains its original index choices and probe counts. For absent key twenty, indices4,7,9,9,9 are all main-loop reads. Clamping repeats the last position three times, making five reads but only three distinct positions. For absent key eight, the path is 4,1,2,3,4: the fifth read is the final equality-only fallback. The first and last read inspect the same position. That fallback executes one comparison; it does not invent an ordering test for its explanatory record.

    For duplicates, a matching index is the first one encountered by this search schedule. It need not be the first sorted occurrence. An eight-item constant array returns index two for its repeated key. Empty input returns false,index−1 and zero work; singleton lookup uses the equality fallback. Sortedness remains an unchecked precondition, so these statements require a nondecreasing input that stays unmodified during the search.

    A complete query census measures logical work

    For each length n below, construct[0,2,...,2(n−1)]. Query every present even value and each of its n+1 missing gaps, represented by−1 and the n positive odd values. This is an exact census of these query classes, not a timing benchmark or a probability distribution over arbitrary keys. The success and missing means use their own denominators. Each query calls the native ordinary search APIs; the report only summarizes their counts.

    Checked virtual schedules and owned actual history

    The pure fibonacci_search_schedule API accepts n without allocating an array. It rejects lengths above PTRDIFF_MAX before schedule arithmetic. For a positive accepted n, the last growth addition sums two predecessors smaller than n, so its covering value fits size_t even when it exceeds the signed index range. Explicit checked addition also protects the growth. Probe computation represents offset−1 as a signed sentinel and clamps before addition, avoiding the former unsigned-wrap idiom. It uses the same mathematical indices on valid inputs.

    Optional C=P counts one whole record per actual read, including repeats and the final equality check. Admission occurs before reading the next input element. Default quota is1000000; zero disables only optional quota. Input values are not copied wholesale. Metadata, vector capacity, allocators and runtime storage are excluded from C, so it is not peak RAM. Records own the values they did read and copies remain independent after input mutation. Ordinary/work calls keep constant auxiliary storage and no history quota; capture errors expose no partial trace.

    Paul E. Black, [Fibonaccian search](https://xlinux.nist.gov/dads/HTML/fibonaccianSearch.html), NIST Dictionary of Algorithms and Data Structures, entry modified14December2020, describes the Fibonacci-sized sorted-array search family and its subtraction scheduling. The native variant starts with the smaller predecessor offset, clamps positions and keeps a final equality fallback; the exact contract and actual counts here describe that implementation.

    P. S. Efraimidis, [(alpha,beta) Fibonacci Search](https://arxiv.org/abs/1012.0259), 2010, introduction, discusses historical arithmetic motivation and explicitly distinguishes sorted-array search from unimodal optimization. Its generalized asymmetric-cost optimum is a different model; this report claims no such optimality for the native exact-match/clamped variant.
