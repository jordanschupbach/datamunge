    Counting Sort: Frequencies, End Cursors and Stable Identities

    Abstract

    Counting sort uses a bounded integer key as an address. Frequencies determine contiguous output blocks, cumulative counts supply their end cursors, and a reverse scan places each input identity into its own slot. We retain the original eight integers and eight named records, derive why this particular placement is stable, and expose the actual native histogram, boundaries and assignments. The record example sorts equal keys directly: arrival indices travel as identities instead of being packed into larger, distinct keys. Measured logical work separates the input length from the bucket range; checked budgets expose the space cost before allocation. Narrow ranges near either signed 64-bit endpoint work without overflowing signed subtraction.

    An eight-element problem with six addressable keys

    Start with [2,5,3,0,2,3,0,3]. The inclusive range [0,5] contains six buckets, although only four keys occur. Buckets for absent keys still take space and prefix work. The sorted output should be [0,0,2,2,3,3,3,5].

    Let L and U be the inclusive key bounds, k=U−L+1 and n the input length. For bucket b=0,...,k−1 define its frequency, start and end:

    \[c_b=\#\{i:a_i=L+b\},\qquad s_b=\sum_{r<b}c_r,\qquad e_b=s_b+c_b.\]

    All copies of key L+b belong in the half-open interval [s_b,e_b). An empty bucket has s_b=e_b. Here key 1 has interval [2,2), and key 2 begins at that same position; there is no unused output slot between them.

    Actual end cursors and the stability proof

    Initialize each mutable cursor p_b=e_b. Visit input indices i=n−1,...,0 and assign the item to j=−−p_(a_i−L). The cursor is decremented before the write. After t items of a particular key have been placed, its cursor equals e_b−t; those items occupy the final t slots of its block. Since exactly c_b items have that key, its last assignment reaches s_b and cannot underflow or collide with another bucket. Every input index is visited exactly once. This proves the output is a permutation with ascending keys.

    For equal-key indices i<j, the reverse scan visits j first and gives it a larger output position. It visits i later and gives it a smaller position. Thus the order of equal keys is preserved. Using a forward scan with these same decrementing end cursors would reverse ties. A different valid design can scan forwards with incrementing start cursors; stability depends on the combination of cursor convention and scan direction.

    Named records with genuinely equal sorting keys

    Retain the original records Ann(1), Bob(0), Cy(2), Dan(1), Eve(0), Fay(1), Gil(2), Hal(0). Supply only [1,0,2,1,0,1,2,0] as keys. The returned output-to-input permutation gathers their names without making arrival index part of the key. A comparison against std::stable_sort uses key alone too.

    A stable digit pass is useful in least-significant-digit radix sorting: after a pass on a more significant digit, ties retain the order already established by less significant digits. This report demonstrates the primitive, rather than asserting that every radix implementation calls these particular overloads.

    Work is controlled by the whole range

    Under the usual fixed-width integer RAM model, counting and placing cost n iterations each, prefixing costs k, and zeroing the bucket arrays also costs O(k). Bounds checks, optional automatic range discovery, owned result copies and identity writes add O(n+k). Thus time and auxiliary storage are Θ(n+k) for nonempty input; n=0 is a constant-time no-bucket case here. These counters are logical work, not timings, total machine instructions or all memory writes.

    Comparison sorting needs Ω(n log n) comparisons in the worst case over arbitrary permutations of distinct keys. That lower bound does not say every input takes that much work. Counting sort uses key values as addresses, so the comparison model does not apply. Its range restriction is the price of that access.

    A trillion-wide range is unsuitable even for two input values. The legacy sorting overloads keep their inclusive hard ceiling of 1,000,000,000 buckets; this is a compatibility limit, not a practical memory recommendation. Their two size_t bucket arrays alone would require about 16 GB at that ceiling on a 64-bit platform. Analysis and tracing default to at most 1,000,000 buckets; tracing additionally defaults to 100,000 placement events. A zero optional cap disables that cap only, leaving the hard ceiling and container limits in force. Returned diagnostics retain three bucket arrays and n identities as well as sorted keys. Temporary arrays and optional events add further peak storage. Allocation can still throw std::bad_alloc below any cap.

    All bounds and keys are validated before bucket allocation or budget checks. The mathematical width is checked using unsigned differences, avoiding signed overflow for extreme bounds and rejecting a full signed-64-bit span safely. Every accepted nonempty diagnostic call returns complete results; it never silently truncates events. Inverted ranges fail even for empty input. Valid empty explicit input retains its bounds but allocates no buckets and skips span and bucket-budget checks, preserving the legacy no-op convention.

    The original deterministic example needs no external dataset: tiny duplicate keys make each cursor and identity inspectable. Exhaustive sequences and random oracle checks test sorting and stability independently of the report figures.

    References and verification scope

    Pat Morin's [Open Data Structures, Section 11.2](https://opendatastructures.org/ods-cpp/11_2_Counting_Sort_Radix_So.html) gives a reverse-placement implementation and its stability/radix connection. The [NIST counting-sort entry](https://xlinux.nist.gov/dads/HTML/countingsort.html) provides the histogram interpretation. The signed bounds, ownership, complete budgets and work definitions above are datamunge contracts.

    Native tests compare all 29,524 ternary sequences through length nine with std::stable_sort on original indices, plus 1,000 random duplicate-heavy inputs. Every actual event is checked on the worked example and random fixtures. Additional controls cover both signed endpoints, all-equal/empty/singleton inputs, exact and one-below budgets, disabled optional caps, full invalid-key validation and unchanged legacy input on failure. Sanitizers check the focused suite. These establish the reported integer properties; no elapsed-time or universal speed advantage is inferred from the operation-count plot.
