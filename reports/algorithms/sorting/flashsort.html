    Flashsort: actual value classes, carried cycles and the insertion tail

    Abstract

    Given finite numeric values, produce an ascending ordering while preserving every element. Value ranges can suggest a useful partial ordering before many comparisons are made. Flashsort maps values into ordered classes, carries values into their class ranges, and finishes with insertion sort. This report inspects native carry records, preserves the original fifteen-value and 2,000-sample examples, and measures the actual classes and finishing work. Equal class occupancies can still lead to very different insertion costs; the class vector also takes linear auxiliary storage for this implementation's default.

    The method: class ranges turn values into destinations

    For n>1 nonconstant values, the implementation chooses m=max(2,int(0.43n)) classes. In exact arithmetic, the linear classification is

    \[k(v)=\left\lfloor\frac{m-1}{v_{\max}-v_{\min}}(v-v_{\min})\right\rfloor, \qquad 0\le k(v)\le m-1.\]

    The native map retains the historical rounded double coefficient and multiplication order when those operations are safe. Integral differences are computed in an unsigned domain of the same width, without signed subtraction overflow. Extreme or tiny floating ranges that make the historical expression unsafe use a scaled long-double ratio. The position is clamped before conversion to an index. Boundary rounding is part of this finite map; it need not equal an arbitrary-precision evaluation of the displayed formula.

    Count each original class occupancy c_k and form exclusive ends E_k=sum_{r≤k}c_r. Class k owns slots [E_{k−1},E_k), with E_{−1}=0. The mutable boundary vector L starts at E. A carried value of class k goes to slot --L_k; the displaced value becomes the next carry. When a cycle closes, scanning for the next unfilled leader continues to the right. Each destination is consumed at most once. The native variant retains its original cycle order and does not first swap the maximum to position zero.

    Three values: follow every carried exchange

    For [2,0,1], m=2 and k(v)=floor(v/2): values 0 and 1 belong to class 0, while 2 belongs to class 1. Counts are [2,1], so the initial exclusive ends are [2,3]. Start by carrying value 2 from slot zero. Its destination is --L_1=2, displacing 1. Then 1 goes to --L_0=1, displacing 0. Finally 0 goes to --L_0=0 and the cycle closes. The array is [0,1,2]; insertion sort has nothing to shift.

    Class ordered does not mean fully sorted

    For [4,1,3,0,2], m=2 again. Class 0 contains four values and class 1 contains only the maximum. The native carry phase produces [1,3,0,2,4]. Every value is in its class range, but three strict inversions remain: (1,0), (3,0) and (3,2). The insertion tail must remove those three inversions, one predecessor shift at a time. Equal keys are not shifted by insertion, but the preceding nonadjacent cycle exchanges give no stability guarantee.

    What the work bound does, and does not, say

    Counting and cumulative ends cost O(n+m). Carry destinations are consumed once and the leader index only increases, so the carry phase has linear work. The last phase is a single whole-array insertion loop. Because ordered classes do not interleave in value, strict inversions occur only within a class. Hence

    \[\text{insertion shifts}=\operatorname{inv}(\text{post-carry array}) \le\sum_k\frac{c_k(c_k-1)}2, \qquad T=O\left(n+m+\sum_k c_k^2\right).\]

    The comparison-only lower bound does not forbid value arithmetic and indexing. Nevertheless, Flashsort's finishing comparisons can be quadratic when distinct values concentrate in one class. Occupancy gives an upper bound; it does not specify their actual order or count only distinct keys. All-equal inputs instead take an O(n) shortcut without a class vector or insertion tail.

    For an ideal model with independent assignments to fixed class probabilities p_k, E(sum c_k²)=n+n(n−1)sum p_k². Balanced probabilities over Θ(n) classes give a linear expectation. This model explains the mechanism; it does not prove a blanket claim for arbitrary clustered inputs, rounded arithmetic, or every distribution normalised by sample-dependent extrema. The experiments below measure actual work instead of using flat bars as a runtime certificate.

    The ordinary implementation stores m integer class boundaries. With m≈0.43n this is Θ(n) auxiliary metadata, even though the carry permutation mutates the original array. Owned trace snapshots add further O(n+m) storage. Neither is constant-space sorting.

    Equal occupancies, different insertion costs

    Construct [0,1,…,q,M] and [0,q,…,1,M], with M=(q+2)(q+1). Both have n=q+2 values and place their q+1 low values in class zero, with the outlying maximum in another class. The native carry order produces [1,2,…,q,0,M] for the ascending low values and [q,q−1,…,0,M] for the descending ones. Their occupancies and squared-occupancy bounds are identical. The actual insertion shifts are q and q(q+1)/2, respectively.

    This family demonstrates the quadratic tail without conflating many duplicate keys with many inversions. Alongside it, native uniform and clustered workloads compare actual occupancy concentration at a common size.     Checked full ranges and complete owned evidence

    The old template formed max−min in the input type. INT_MAX−INT_MIN overflowed signed int before conversion. Finite floating inputs could also overflow their range or produce an infinite coefficient on a tiny range, followed by an invalid integer cast. Bounded sanitizer probes reproduce those failures in the frozen original. The checked map keeps ordinary safe results and carries intact while handling those full ranges safely.

    Floating inputs must all be finite, including a singleton. Invalid data is rejected before mutation; n must fit the legacy int index domain. The vector signature and existing sorting_extra.hpp include remain available. The implementation supports arithmetic types other than bool; it is not a generic comparator or payload-key sorting interface.

    The optional trace validates and scans extrema once, then checks complete capture C=5n+2m before copying or sorting. Shortcuts use C=2n and have no class arrays or carry history. The default entry cap is one million; zero disables only that optional cap. Owned records are independent copies, and failure returns no partial trace. Ordinary in-place sorting and work counters do not allocate history or impose that optional quota.

    What this establishes

    The original sorted outputs and sample are preserved, while the plot now represents actual sorter classes. Tiny traces show the carried values and the difference between class order and full numeric order. Measured shifts support the inversion identity and expose a quadratic family with the same occupancies as an easier family. Finite-range validation removes observed undefined behavior without changing the historical safe path. These checks establish specific arithmetic and algorithmic properties; they do not establish that this sort is fastest on any processor or that arbitrary skewed data has linear work. No external dataset is needed for these controlled sorting questions.
