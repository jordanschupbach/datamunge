    Burstsort: Actual Buckets, Bursts and Prefix Depth

    Abstract

    Burstsort keeps related strings in leaf buckets and creates deeper trie nodes only when a bucket exceeds its capacity. We retain the original nineteen-word example and its first-letter plot, but inspect actual native nodes, slots and burst events instead of inferring the trie from first-letter counts. The core now uses string-index buckets, flat node ownership and explicit work stacks, so long prefixes do not require recursive insertion, collection or destruction. Measured controls show why the trie is not always shallow: eight identical strings stay in a bucket, while nine can create one node per prefix byte. The report discusses locality without claiming an unmeasured cache-speed win.

    The original words: one real burst under a

    The input contains nine words beginning with a. The default capacity is eight, and overflow means strictly greater than eight. The ninth a-word, almond, arrives at original index eighteen and creates a child for prefix a. Its second-byte slots are l, p, r and v; the p bucket contains six strings and remains a leaf. Other first-byte slots remain root buckets.

    Insertion follows one byte at a time. A leaf slot holds original string ids; when it overflows, a new child consumes the slot byte and receives those ids in their actual encounter order. Strings ending at a node go into its separate terminal list. Collection emits terminals first, then slots in unsigned byte order. A leaf is sorted by full string value, with original id breaking equal value ties; a child is traversed before the next byte slot. This produces ordinary byte-lexicographic order, with prefixes before their extensions.

    The old sorting_dist include remains a compatibility entry point. The ordinary one-argument API keeps its threshold eight. A separate configured entry point accepts a positive capacity and an optional whole-call node cap. No overload ambiguity is introduced for existing function-pointer or callback uses.

    Preserve the first-letter plot and vary capacity

    Smaller capacities create more structure and more directory scans, while larger capacities leave more full-string sorting inside leaves. The counts alone cannot select a universal fastest threshold. In this implementation, full string comparisons may revisit already shared prefixes; their invocation count is not a byte-inspection count. std::sort call counts can also differ between toolchains. The published [Sinha and Zobel study](https://people.eng.unimelb.edu.au/jzobel/fulltext/acmjea04.pdf) examines cache-conscious implementations and workloads; its measured speedups are not measurements of this C++ variant or these nineteen strings.

    A discontinuity: eight copies versus nine copies of a long string

    For capacity B=8, eight identical strings remain in one root bucket. For nine copies of a length-L string, each occupied slot overflows, creating another child until the strings terminate. The final chain has L+1 nodes, including the root, L bursts, and nine terminal ids at depth L. It is not a shallow trie.

    Each original id consumes each routed prefix byte only once, including later redistribution. For this duplicate family the actual counts are

    \[Q=L+1,\qquad R=9L,\qquad V=9(L+1),\qquad S=256(L+1),\]

    where Q is node count, R is routing-byte reads, V is insertion work items, and S is collection directory checks. The factor 256 comes from this variant's dense byte directories, even when a node has only one occupied slot.

    The native implementation uses a flat node arena, occupied-slot records and explicit insertion/collection stacks. Child relationships are indices, so unwinding and destruction do not recursively follow a deep chain. Buckets hold input ids rather than full string copies; after collection each full string is copied once into output, followed by a final swap for the in-place API. Tracing additionally owns the input and actual records. Parent links avoid storing every complete node prefix; a requested prefix is materialized in linear work in that prefix's depth.

    Writing D for total input bytes, n for string count and Q for actual nodes, routing and directory work is O(D+n+256Q), plus the cost of full-string leaf comparisons. A leaf of k strings has O(k log(k+1)) comparison calls; the byte cost of one call depends on those strings. Algorithm storage is O(D+n+256Q), with O(D+n+Q) additional owned trace data. This accounting does not claim that a root bucket or its string data necessarily fits a hardware cache, or that the trie depth is bounded independently of input length.

    Terminals, binary bytes and failure boundaries

    Ending a string is distinct from encountering byte zero. The empty string terminates at the root; a terminates at prefix a before aa and ab are collected. Embedded zero and high-bit bytes remain ordinary data. Sorting is byte-lexicographic, without Unicode normalization or language collation.

    A positive node cap includes the root and throws before a new child would exceed it. No partial output is swapped into the caller's vector. Host allocation failures likewise preserve its original values: an isolated native test injects failures at all 103 allocation positions across default and configured sorts, checks the unchanged input, then retries successfully. Empty/singleton inputs preserve the original shortcut and do not fabricate root nodes or routing work. A zero configured capacity is always rejected.

    The native tests compare 19,531 exhaustive small arrays at three capacities with stable global string order and an independent static prefix-frequency partition. The (B+1)-th arrival sharing a prefix independently determines its burst time, so the checker verifies actual chronological events as well as final topology. Further tests cover 1,000 random binary/duplicate arrays, all 256 byte slots, exact threshold and node limits, malformed prefix paths, the 10,000-byte chain, existing distribution-sort cases and UBSan. These explicit and generated inputs explain the mechanism without a forced dataset.
