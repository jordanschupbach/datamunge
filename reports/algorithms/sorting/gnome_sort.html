    Gnome Sort: The Pointer Walk and Its Exact Cost

    Abstract

    Sort a sequence of integers while keeping equal values in their original order. A short loop can do this by moving one pointer forwards over ordered pairs and backwards after exchanging an inverted pair. This report follows actual native execution on three values, repeats the original seven-value walk, and checks stability through carried identities. A decreasing potential explains the exact cost: n values with I strict inversions require n+2I loop visits. Controlled input families, key-comparison counts and resource limits show what that identity does and does not measure. Every table and figure is generated by complete C++ programs.

    Follow two actual exchanges

    Start with [3,1,2] and pointer i=0. At the boundary, advance without comparing keys. Otherwise compare a[i−1] and a[i]. If they are ordered, advance; if they are strictly inverted, exchange them and step back. The native trace records that executing loop, including the before-pair values and their original identities. It does not run another sorting loop to reconstruct a history.

    Why the walk stops, and why it is stable

    Before each visit, the prefix a[0..i) is sorted. Advancing at the boundary creates a sorted one-element prefix. Advancing over an ordered pair extends an already sorted prefix. After a swap and backward step, the shorter prefix excludes the changed positions and remains sorted. When i=n, the whole sequence is sorted.

    Let I be the current number of strict inversions: pairs of positions p<q with a[p]>a[q]. Exchanging a strict adjacent inversion removes exactly one inversion; relations with every other value have the same total contribution. Equal values are never exchanged, so equal-key identities cannot cross.

    The pointer can retreat, but the following integer potential cannot increase:

    \[P=n-i+2I.\]

    An ordered forward visit increases i by one without changing I, decreasing P by one. A swapping backward visit decreases i by one and I by one, also decreasing P by one. P starts at n+2I0, remains nonnegative, and is zero after sorting stops. Thus every visit consumes exactly one unit of the initial potential:

    \[S=n+2I_0,\qquad B=I_0,\qquad F=n+I_0,\qquad C=S-Z.\]

    Here Z counts visits at index zero. For nonempty input it is one plus the number of strict new prefix minima in the original sequence: each such value crosses the entire earlier prefix and causes one extra return to zero. Equal minima do not cross. For empty input every work count is zero.

    The retained boundary/ordered-pair rule is documented by [Paul E. Black’s NIST entry](https://xlinux.nist.gov/dads/HTML/gnomeSort.html), which also records Hamid Sarbazi-Azad’s 2000 Stupid Sort newsletter article. The potential and the controlled counts here make the vague phrase “nearly sorted” precise: time is linear when I0=O(n). Repeated forward checks mean this loop need not perform the same number of comparisons as an ordinary insertion sort.

    The scalar API still returns an owned sorted copy. It sorts that owned buffer in place using constant auxiliary state, but passing an lvalue copies n values. gnome_sort_run() additionally creates and returns n original-position labels; that output and its initialization cost O(n). The trace adds O(H) fixed-size records, rather than retaining a complete n-value snapshot for each visit.

    Control the inversions and predict the work

    The native adjacent_sort_inputs() generator returns four owned arrays containing 0 through n−1. Ascending input has I0=0; descending input has I0=n(n−1)/2. One middle adjacent inversion has I0=1 for n≥2. Moving the minimum to the last slot has I0=n−1. Consequently their visit counts are n, n², n+2 and 3n−2, respectively, with the stated empty/singleton exceptions.

    Visits and key comparisons are different quantities

    Two four-value inputs can have the same inversion count but different boundary counts. [4,1,2,3] and [3,2,1,4] each have three inversions and ten visits. Their strict new prefix minima differ, producing two versus three boundary visits and therefore eight versus seven key comparisons. An all-equal input has no swaps: its four visits include one boundary step and three comparisons.

    Complete histories and whole generated inputs have different units

    gnome_sort_trace() captures fixed-size initial, step and stop records online. A completed S-visit execution has S+2 records; there is no full-vector snapshot per visit or numerical replay. Before each complete append, the optional quota and container capacity are checked. Even the final metadata append can throw: no partial history or ordinary result is returned. Zero turns off the optional record quota; it does not suppress recording.

    A quota counts complete records, not numeric entries, bytes or peak RAM. Inputs, the root object, ordinary sorted values and identity output, constant working state and allocator overhead are excluded. Input copying and identity allocation can happen before a history limit is reached. The generator instead checks the whole 4n integer entries across its four arrays before allocating them. Its entry quota also excludes vector objects and allocator overhead. These controls have different meanings even when their numeric limits happen to coincide.

    What the experiments establish

    A sorted prefix gives correctness, strict adjacent exchanges give stability, and the potential counts every forward and backward visit. The original example, identity-labelled duplicates, controlled inversion families and boundary counts agree with those derivations. Independent development tests use direct stable ranks and pairwise inversion counts; actual recorded transitions also certify the prefix invariant and one-unit potential decrease at every visit.

    There is no external dataset in this experiment. Controlled integer inputs give known inversion counts and exact predictions, including empty and repeated values. The ordinary sort keeps constant auxiliary state beyond its owned input/output, while diagnostic identities and retained history have their separate stated storage costs. A short loop is easy to describe; its visit count, key comparisons and retained records are still different quantities.
