    Dijkstra’s Algorithm: Settled Vertices and Stale Heap Entries

    Abstract

    Given a directed network with nonnegative travel costs and a starting vertex, we want the cheapest cost and a route to every reachable destination. Choosing a cheap immediate edge alone cannot identify the cheapest complete route. Dijkstra’s algorithm instead settles the smallest accumulated cost on the current frontier. A three-vertex example shows how improving a route leaves a stale heap entry without expanding a vertex twice. We retain the original six-city network and reconstruct its route of cost eleven. Actual heap removals and edge inspections expose the implementation’s tie rules and work. Zero-cost cycles, unreachable vertices, invalid weights, overflow and malformed predecessor records test its boundaries. Sparse bands and parallel-arc workloads distinguish the familiar simple-graph complexity from the larger heap possible in a multigraph.

    Start with three vertices and one improved route

    Let source 0 have a direct edge to target 1 of cost four and an edge to vertex 2 of cost one. The edge 2→1 costs one. After expanding the source, the heap contains tentative routes (1,2) and (4,1). Removing (1,2) discovers a cheaper route to target 1, of cost two, and pushes (2,1). We then settle 1 at cost two. Finally the old (4,1) entry is removed and skipped: its key four is larger than the current distance two.

    A vertex is settled once, while its id can occur in several heap removals. The trace below comes from the same kernel as ordinary dijkstra(), with no replay of prefixes and no report-local shortest-path implementation. Exactly seven events are recorded: four removals plus three edge inspections.

    Why settling the nearest frontier is safe

    For vertices 0,...,V−1, let delta(s,v) be the least total edge cost of a source-to-v path, or positive infinity when no such path exists. Store d[s]=0 and all other tentative distances as infinity. Relaxing an arc (u,v,w) compares candidate=d[u]+w with d[v]; a strict improvement changes the distance and parent and pushes the new (candidate,v) heap entry. Tentative finite labels always correspond to discovered routes, so they are upper bounds on the true optimum in exact arithmetic.

    Suppose the minimum fresh entry u had a shorter true route. On that route, let y be the first vertex outside the settled set and x its settled predecessor. Expanding x already gave y a tentative cost at most the cost of the route prefix. Nonnegative remaining costs make this at most the full route cost, which was assumed smaller than d[u]. Then y would be a smaller frontier entry, contradicting the choice of u. Thus a fresh minimum has its final distance. Strict improvements and nonnegative weights ensure a settled vertex never needs a new expansion. Zero weights are valid; strict comparison prevents equal-cost cycles from changing parents.

    The implemented frontier is a binary min-heap ordered by (distance,vertex). Smaller vertex ids break equal-key ties. Outgoing arcs preserve input order, and equal-cost candidates retain the first predecessor. A later strict improvement adds a new entry; the older one remains until it is removed. The stale test is stored_key > current_distance. There is no decrease-key, no full queue snapshot and no early target stop: the single-source API drains the heap and returns all reachable distances.

    [Dijkstra’s original 1959 paper](https://doi.org/10.1007/BF01386390) constructs routes in increasing distance order and stops at a requested destination; it also discusses directed branch lengths. This implementation uses that settling principle for a complete source traversal with a lazy heap. The floating-point implementation compares rounded double additions, so the exact-arithmetic proof does not promise exact-real costs for arbitrary doubles.

    Zero-cost ties, unreachable vertices and invalid input

    For equal tentative costs, the heap’s smaller vertex id settles first, regardless of the order of the source’s adjacency entries. In the next example, the source lists vertex 2 before vertex 1, both at cost one. Vertex 1 nevertheless settles first and supplies vertex 3’s parent. Zero cycles and duplicate arcs produce inspections, but equal candidates never push new entries. Vertex 4 is isolated, so its distance is infinity and its reconstructed route is empty.

    A negative edge invalidates the settling proof. In a separate three-node control, 0→1 costs two, 0→2 costs five and 2→1 costs minus six. An irrevocable settlement of vertex 1 at cost two would be premature: the route through vertex 2 costs minus one. Dijkstra rejects that graph; the existing Bellman–Ford API returns minus one. This illustrates the broken invariant, rather than claiming an unchecked variant must return one particular wrong answer.

    All endpoints and weights are checked, including arcs in unreachable components, before adjacency allocation. NaN, either infinity and negative weights raise invalid_argument. If an examined sum of finite nonnegative costs overflows, the kernel raises overflow_error, even when the candidate would not beat an already known shorter route. It does not silently turn a reachable cost into the infinity marker. A finite DBL_MAX route is valid.

    The public two-field ShortestPathResult layout is unchanged. Safe path recovery now bounds traversal and validates visited indices, finite nonnegative distances, vector alignment and cycles. Out-of-range and positive-infinity targets retain the original empty-return convenience. Without a stored source or edge list, this function checks structural safety; it cannot certify that a manually supplied sentinel is the intended source or that arbitrary parent costs satisfy edge recurrences.

    Count the work rather than infer it from a timing curve

    Let R be the number of strict improvements, E_r the number of outgoing arcs examined from reachable settled vertices and V_r the number of reachable vertices. A full successful execution has

    \[\text{pushes}=\text{pops}=R+1,\qquad \text{stale pops}=R+1-V_r,\qquad R\le E_r\le E.\]

    The extra push is the initial source entry. Every improvement creates one entry, and draining the heap removes every entry. Each reachable vertex accounts for one fresh removal; the rest are stale. The peak heap size is at most R+1. Validation and adjacency construction still inspect/store all E input arcs, including unreachable components.

    Binary heap operations take logarithmic time in the live entry count. Thus a safe multigraph bound is O(V+E+(R+1)log(R+2)), or O(V+E+(E+1)log(E+2)) after eliminating R. Storage is O(V+E). For simple graphs, E is at most quadratic in V, giving the familiar O((V+E)log V) bound. The original report’s unrestricted heap-size/log-V claim needs this distinction when arbitrarily many parallel arcs are allowed. Counters count logical pushes, removals and inspections, not comparator calls, elapsed time or a guaranteed constant per heap operation.

    For a forward band, include u→u+d for d=1,...,w when the destination exists, and give every arc cost one. With n>w, the exact edge count is wn−w(w+1)/2. Every non-source vertex improves once, the heap peaks at w, and delta(0,v)=ceil(v/w). The existing canonical band generator supplies the inputs; no graph-building algorithm is reimplemented in the report.

    Two vertices can still produce a large lazy heap

    Take m parallel arcs 0→1 with descending weights m,m−1,...,1. Expanding source 0 improves vertex 1 once per arc. Before vertex 1 can be removed, the heap therefore contains m entries, even though V=2. The first removal settles vertex 1 at cost one; the other m−1 are stale. The exact counts are m inspections, m improvements, m+1 pushes/removals, a peak heap of m and two settled vertices for positive m. This proves that a lazy heap is not generally bounded by the number of vertices. It does not alone prove a lower bound on comparator work. The figure uses base-two logarithms of the positive counts to distinguish heap growth from the constant two settled vertices; the table retains exact integers.

    The canonical workload generator checks the complete edge count before allocation. Integer weights stay exact through count 2^53; an optional one-million-edge output cap defaults on. The trace separately budgets actual events as pop records plus inspected-edge records. Its default is one million events, and zero disables only that optional cap. Budgets are checked before the next operation, so the exact m-arc history needs 2m+1 events. Result arrays, adjacency and settled-order storage are outside that history count. An exhausted budget raises length_error with no partial trace returned. Ordinary dijkstra() allocates no trace histories.

    What was verified and what remains a convention

    Native tests enumerate all 4096 three-vertex directed graphs whose six possible non-loop arcs are absent or have costs zero, one or two. For every source, independent Floyd–Warshall distances match both ordinary and traced Dijkstra: 12,288 source traversals. A multiset-based event certificate checks every recorded minimum removal, original arc, prior distance/parent, candidate, strict-improvement outcome and resulting heap size. The original six-city graph, zero cycles, duplicate arcs and tie order receive explicit checks. The existing 500 seeded Bellman–Ford comparisons remain in the suite.

    Closed-form band and parallel-arc families check final distances, selected arc identities and work conservation. Exact/one-short event caps, complete input validation, overflow priority, finite maximum/subnormal costs, negative zero, malformed predecessor chains and owned trace copies cover boundary behavior. A malformed public record can no longer force unchecked parent indexing or an infinite reconstruction loop.

    The original finite distances, predecessor conventions, public function signatures, two-field result layout and formatting remain available. The new trace distinguishes discovery, settlement and obsolete entries; it does not conflate nine removals with six settled cities. Nonnegative finite costs make greedy settlement valid, while explicit floating-point and history limits keep failures visible rather than presenting them as unreachable routes.
