    Diffie–Hellman: Agreement, Exact Arithmetic and What the Transcript Does Not Prove

    Abstract

    Two parties want to compute the same value while exchanging only public messages. They need an algebraic agreement rule, and they must distinguish that rule from secrecy and peer authentication. Finite-field Diffie–Hellman uses modular powers so that both parties obtain g^(ab) modulo p. We retain the original p=23 example and the larger 31-bit exchange, then actually recover the latter's sample exponent with an existing core discrete-log solver. Native traces expose square-and-multiply states and exact operation counts. Bounded group cycles show periods and tiny subgroups rather than using a scattered plot as evidence of hardness. A two-session substitution demonstrates the missing authentication. All computations use the canonical uint64 core; these reproducible, variable-time examples are arithmetic illustrations, not a secure key-agreement implementation.

    The original agreement, with visible public messages

    Take p=23, g=5, Alice's private exponent a=6 and Bob's b=15. Alice publishes A=56 mod 23=8; Bob publishes B=515 mod 23=19. Alice computes B6 mod 23=2, and Bob computes A15 mod 23=2. The exponents are shown here so the worked example can be checked; an actual protocol keeps them private.

    For a prime p and a nonzero group element g,

    \[B^a=(g^b)^a=g^{ab}=(g^a)^b=A^b\pmod p.\]

    The identity establishes agreement. It does not establish that an observer cannot compute the value or that either peer has the expected identity. Recovering a discrete logarithm suffices to break the exchange; the passive computational target is the shared value given g, p, A and B. We do not infer that recovering an exponent is the only possible route to that target. [Diffie and Hellman's original paper](https://web.mit.edu/6.857/OldStuff/Fall03/ref/diffie76new.pdf) itself distinguishes the known direction from its unproved converse.

    The program also retains the original 31-bit prime p=2^31−1 with g=7. The same public values and shared residue reappear. The existing baby_step_giant_step_trace() takes only that public generator, modulus and Alice's public value, recovers the sample exponent, and recomputes the shared value. No private exponent is passed to the recovery call.

    Follow the actual square-and-multiply states

    Write e as a sum of binary powers. At each low-bit-first step, the running base represents g(2i) modulo m. When bit i is set, multiply it into the accumulator; then square the running base and shift the remaining exponent. The invariant is

    \[\text{accumulator}\times\text{running}^{\text{remaining}} \equiv g^e\pmod m.\]

    For e=6, binary110, the low bits are zero, one, one. The running residues are 5,2,4 and the accumulator becomes 1,2,8. The existing loop also computes a final, unused running-base square 16. The trace retains that actual work; it does not silently substitute an optimized loop. Raising Bob's public 19 to the same exponent instead ends at the shared residue 2.

    The full product of two uint64 values fits in unsigned 128 bits. Reducing that complete product avoids an intermediate 64-bit wrap. This is exact integer arithmetic on the supported compiler, including moduli near 2^64; it says nothing about secrecy. The scalar helpers and trace share one kernel.

    A small power plot has visible group structure

    For an element of order r, g(x+r)=gx. The full generator 5 modulo23 has order 22: exponents 0 through 21 enumerate all nonzero residues exactly once. The original plot used 0 through 22 and therefore included the identity twice. With g=4, the order is11; with g=22 it is2; g=1 has order 1. These are exact periods, not evidence of random behavior. A tiny table immediately inverts the original public values 8 and 19 to exponents 6 and 15 modulo 22.

    Matching residues do not authenticate a peer

    An active intermediary can replace each public message and establish two separate arithmetic sessions. In this control Alice keeps a=6 and Bob b=15. The intermediary sends 513=21 to Alice and 57=17 to Bob, all modulo23. Alice agrees on 18 with the intermediary; Bob agrees on 15 with the same intermediary. Both local agreement checks pass, while Alice and Bob have different values. The arithmetic alone never established whom they reached.

    The legacy wrappers accept these bases and perform arithmetic; they do not authenticate or validate peers.

    A received zero can force zero for positive exponents; one always gives one; p−1 reveals exponent parity in these examples. Range and subgroup validation belong to a fully specified group/protocol. For known safe-prime FFDHE groups, [RFC 7919 section 5.1](https://www.rfc-editor.org/rfc/rfc7919.html#section-5.1) specifies 1<Y<p−1; its discussion of unknown groups requires more than that range check. Our toy full-group generator and arithmetic APIs do not claim to implement that RFC. Authenticating the exchange and deriving a usable key are separate tasks absent from this demonstration.

    Count actual work and check the full-width arithmetic

    For m>1 and positive exponent e, let L=bit_width(e) and w=popcount(e). The retained right-to-left loop performs exactly L squares and w accumulator products, including its final unused square:

    \[N_{\mathrm{products}}=L+w.\]

    At the same L, a power-of-two exponent takes L+1 products while an all-one exponent takes 2L. Thus the implementation is not constant-time; this plot counts operations, without treating them as measured processor timings. Exponent zero has no products and returns one for m>1; m=1 returns zero without products for any exponent. Both scalar and trace reject m=0. The work sweep uses modulus 2^64−1 as an arithmetic control, not a prime field.

    Contracts and verification

    The established dh_public_key(), dh_shared_secret(), mod_pow() and mul_mod() names remain available through the original include. The power wrappers retain arithmetic-only behavior, including composite moduli, zero exponents, zero bases and modulus one. The modular product now rejects a zero modulus before remainder evaluation. These raw APIs do not sample private exponents, validate a protocol group or peer, authenticate messages, supply a KDF or provide constant-time arithmetic. The trace deliberately exposes exponent bits. Matching residues on p=1 or on a composite modulus are algebraic results, not a validated prime-field agreement.

    A complete effective bit count is checked before trace allocation/powering; its default cap is 64, and modulus one has zero effective bits. The cycle API separately checks a prime p>=2 and 1<=g<p, then applies an online default one-million-value cap. It emits the identity once and performs a closing product; enumeration costs O(order) storage/products plus its primality check. Zero disables only optional caps; vector capacity checks remain. The scalar powering driver uses O(1) storage and O(log(e)+1) fixed-word operations; traces own O(log(e)+1) records. Multiprecision bit-operation cost is not measured here. No random dataset fits these exact finite controls.

    Nine native tests check 72,900 small exchanges, including composite rings, and 103,275 complete small power traces against repeated multiplication and the state invariant. Addition-only multiplication with an independent left-to-right power driver checks 5,000 full-width products and 500 powers. Every nonzero element of every prime through 127 is enumerated independently; a full-width prime's order-two element tests the closing product near 2^64. An optional Python development oracle separately verifies 20,000 arbitrary- precision product/power controls, including zero and full-width moduli. Original values, periods, subgroup collapse, two-session substitution, complete trace caps, online cycle caps, edge conventions and owned copies are checked. These validations establish arithmetic and report behavior; they do not turn the toy implementation into a secure cryptographic protocol.
