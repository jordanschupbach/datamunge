    Fermat Factorization: Exact Squares and Actual Trial Counts

    Abstract

    Given an integer, find a proper factor pair whose product recovers the input. Divisors are easy to verify but can be expensive to discover. Fermat searches for a difference of squares, making nearby odd factors especially accessible. We begin with the three actual square tests that split 5959 into 59 times 101, then retain the original two factorizations and seven factor-gap examples. The native solver supplies exact states and counts directly. Prime inputs, composite factors, a capped composite, large near-squares and optional capture limits show precisely what each returned result establishes. Every figure is produced by its complete editable C++ program.

    Three square tests and one rectangle

    For odd n, test integer a from the exact ceiling square root upward. Put d=a²−n and b=floor(sqrt(d)). The trial succeeds exactly when b²=d, giving n=(a−b)(a+b). For n=5959, start at 78: 78²−5959=125 is not a square. The next difference is 282, and the third is 441=21². Thus 80²−21²=5959 and the factors are 59 and 101. This takes three square tests and two increments. Zero increments still means one test.

    The native diagram uses the actual successful a and b for its equal-scale geometry. The remaining L-shaped area can be rearranged into a rectangle of sides a−b and a+b. Its area agrees with the factor certificate below. The three boxes are actual captured solver rows, rather than a local search.

    Why the search finds the closest pair

    An odd factorization n=pq, 1≤p≤q, gives integer A=(p+q)/2 and B=(q−p)/2 with A²−B²=n. Conversely, a square hit gives positive odd factors a−b and a+b. Every pair has A≥sqrt(n). Scanning integer a in ascending order therefore finds the pair with minimum A, equivalently the closest factor pair. That pair can contain composite factors: for 945, the first split is 27 times 35. This is a splitting algorithm, not a complete prime factorization.

    Let A_min denote that first pair's A, and a0=ceil(sqrt(n)). Without a trial cap, the exact number of increments is D=A_min−a0 and the number of tests is T=D+1. The continuous excess A_min−sqrt(n) is not D; because A_min is an integer, D=floor(A_min−sqrt(n)). For the returned pair,

    \[A-\sqrt n =\frac{(\sqrt q-\sqrt p)^2}{2} =\frac{(q-p)^2}{2(\sqrt q+\sqrt p)^2} \approx\frac{(q-p)^2}{8p}\qquad(q-p\ll p).\]

    The approximation explains a small-gap quadratic trend at roughly fixed p. It is neither an exact integer count nor a universal complexity formula for any chosen factorization: a different pair may be closer.

    A trial limit says nothing about primality

    Every odd n has the trivial pair 1 times n at a=(n+1)/2. If an exact ascending search reaches it without an earlier hit, n has no nontrivial pair and is prime. The TrialLimit stop says only that the allowed tests ended first. Returning n alone cannot distinguish these two outcomes. For 13, the first three tests miss and the fourth reaches the trivial pair. For 5959, a budget of two misses and three finds 59 times 101.

    The preserved legacy entry point uses a five-million-test cap. The composite 3000000021=3 times 1000000007 still returns n at that cap. There is no need to run until its distant pair merely to know it is composite: the small factor three is already an exact certificate.

    The even branch returns two with zero square tests. For n=2 the other factor is one, so proper_split is false. Integers congruent to two modulo four cannot be a difference of integer squares; the even shortcut is a separate operation. Odd squares succeed immediately with b=0.

    Exact roots at the width boundary

    A uint64 input can need a=232, whose square is 264. Keeping a²−n in uint64 would lose that value. The core uses unsigned 128-bit differences and the reusable integer_sqrt_u128 API. It brackets the root using bit width and compares middle≤n/middle in an integer binary search. The exclusive upper sentinel can be 2^64 in the wider type, so even the maximum unsigned 128-bit value is handled without squaring that sentinel.

    For odd uint64 n≥3, the trivial pair is reached by a=(n+1)/2≤2^63. Every earlier tested a is no larger, b fits uint64, and the difference fits unsigned 128 bits. The implementation checks the budget before advancing an unused next a or trial count. These are fixed-width exact integer statements, not floating error tolerances.

    The former report's independent counter used ceil(sqrt(double(n))). At n=(232−1)²+2=18446744065119617027, that expression rounds its starting a down to 232−1. Its subtraction then wraps in unsigned 128 bits, and its floating square root converts out of uint64 range. A strict sanitizer probe reproduces that failure. This was a report-local counter defect; the former core already corrected its initial integer root. The new report has no local counter and reads every count from the solver.

    The diagnostic floating ceiling below only displays that starting-value mismatch; it never performs the unsafe wrapped subtraction or cast. The exact wide API also handles arbitrary differences beyond Fermat's input range, as shown by the final 2^128−1 root check.

    Work, optional history and explicit limits

    fermat_factor retains its compiled one-argument signature and five-million square-test default. fermat_factor_work returns the same solver's counts without optional history. fermat_factor_trace captures one whole FermatStep per actual odd square test, in the same pass. All inputs require n≥2 and a positive trial budget; the historical meaningless returns for zero and one are now rejected. Even fast paths validate the controls too.

    C=captured_entries=rows.size() counts whole records. The trace admits each record before its square/root work. Its default one-million-record quota is independent of the five-million-test budget. A zero max_entries disables only that quota; it does not disable the trial budget. A failed admission or allocation throws without returning a partial trace. This is a count of owned records, excluding scalar metadata, vector capacity, allocators and runtime storage, so it is not a peak-memory guarantee.

    For this fixed uint64/uint128 representation, each root uses at most 63 division comparisons. Ordinary/work calls take O(T) such fixed-word work and constant auxiliary storage; a successful trace takes O(T) records. With arbitrary-size integers, root and multiplication costs depend on the bit length and cannot be folded into a unit-cost claim. In the prime case, reaching (n+1)/2 takes order n tests, exponential in input bit length. The budget bounds actual work, while the optional quota bounds captured records. Factor-gap plots are measured work on selected inputs, not timing benchmarks or a claim that this beats general factorization methods.

    Interpretation and sources

    The native API preserves the original factor outputs and original full-program stdout on their valid fixtures, while replacing the report-local counter with actual solver work. The development tests freeze 4626 legacy factor lines and compare independent divisor-pair counts, every captured square identity, full-width root boundaries, budgets, quotas and ownership. An optional Python math.isqrt oracle checks exact roots using arbitrary-precision integers; it is a development check and is not a report runtime dependency.

    The reusable additions live in number_theory_extra.hpp and integer_arithmetic.hpp. Trial division and Pollard p-minus-one are unchanged. Fermat's splitting method is distinct from Fermat's congruence-based probable primality test. The next report covers that separate test.

    C. Pomerance, [A Tale of Two Sieves](https://math.dartmouth.edu/~carlp/PDF/paper109.pdf), Notices of the American Mathematical Society 43(12), 1996, pp.1473–1485, particularly “Fermat and Kraitchik” on p.1474, gives the difference-of-squares identity and its close-divisor advantage. The identity motivates this native finite-budget variant; the count derivation, exact-width guards and capture contract above describe this implementation.

    Python 3.14's [official math.isqrt contract](https://docs.python.org/3.14/library/math.html#math.isqrt) specifies the exact floor root used for the independent development oracle. The native division-based implementation has the same mathematical root contract over unsigned 128-bit inputs and uses no Python dependency.
