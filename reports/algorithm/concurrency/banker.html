    The Banker's Algorithm: Avoiding Deadlock by Staying Safe

    Abstract

    Dijkstra's banker's algorithm (1965) grants a resource request only if the system stays in a safe state: one from which every process can still finish, in some order, even if each asks for its full declared maximum. We prove that the greedy safety check, which finishes any process that fits, never misses a safe order, and that a safe state cannot deadlock. On the classic five-process textbook instance the state has 16 safe orders out of 120. For two processes sharing one resource type the unsafe states form a rectangle that we derive in closed form, and every deadlock lies inside it. Finally a simulation of four processes acquiring two resource types a unit at a time shows the trade-off: granting whatever is free deadlocks in every run once resources are tight, while the banker never deadlocks and completes more jobs per step even before the greedy policy gets stuck.

    Safe states

    A system has \(n\) processes and \(m\) resource types. Process \(i\) holds \(\mathit{Alloc}_i\in\mathbb N^m\) and has declared a maximum claim \(\mathit{Max}_i\), so it may still ask for \(\mathit{Need}_i=\mathit{Max}_i-\mathit{Alloc}_i\). The free units are \(\mathit{Avail}\). The state is safe if there is an order \(p_1,\dots,p_n\) of the processes with

    \[\mathit{Need}_{p_k}\le\mathit{Avail}+\sum_{l<k}\mathit{Alloc}_{p_l}\qquad(k=1,\dots,n),\]

    componentwise: even if every process asks for everything it may, each in turn can be given its whole need, run to completion and release its allocation.

    *A safe state cannot deadlock.* In a deadlock a set of processes each wait for units held by others in the set, forever. Take the first process of the set in a safe order: everything it could ask for fits in the free units plus what earlier processes (outside the set, so able to finish) release, so it is not stuck after all.

    *An unsafe state need not be deadlocked yet*, but some sequence of requests, each within the declared claims, leads to deadlock. The banker therefore refuses any request whose result is unsafe and makes the requester wait.

    The greedy check is exact

    The safety algorithm keeps a work vector \(W\), initially \(\mathit{Avail}\), and repeatedly picks any unfinished process with \(\mathit{Need}_i\le W\), adding \(\mathit{Alloc}_i\) to \(W\). It answers "safe" when all processes finish. Choosing the wrong process first cannot hurt: finishing a process only increases \(W\). Formally, suppose a safe order exists but greedy stops with a set \(F\) finished and \(W=\mathit{Avail}+\sum_{i\in F}\mathit{Alloc}_i\). Let \(p\) be the first process outside \(F\) in the safe order. All processes before \(p\) in that order are in \(F\), so \(\mathit{Need}_p\le\mathit{Avail}+\sum_{l<k}\mathit{Alloc}_{p_l}\le W\), and greedy could have finished \(p\). This contradiction shows greedy succeeds whenever any safe order exists, in \(O(n^2m)\) time.

    The number of safe orders can still be large, and banker_count_safe_sequences() counts them by a dynamic program over subsets: the work vector after finishing a set depends only on the set.

    The textbook instance

    The block uses the five-process, three-resource example of Silberschatz, Galvin and Gagne, finds a safe order, counts all of them, and decides three requests in turn.

    Available (3, 3, 2). Safe: true. Greedy order: P1 P3 P4 P0 P2. Safe orders: 16 of 120.

    The state is safe, and greedy finds the order P1, P3, P4, P0, P2: P1's need \((1,2,2)\) fits in \((3,3,2)\), and each finished process adds its allocation to the pool. It is one of 16 safe orders among the \(5!=120\); every one of them must start with P1 or P3, the only processes whose needs fit in the free units.

    Granting P1's request \((1,0,2)\) keeps the state safe but halves the safe orders to 8, since the free pool shrinks to \((2,3,0)\). P4's request \((3,3,0)\) cannot even be considered: only \((2,3,0)\) is free, so P4 simply waits. P0's request \((0,2,0)\) is for units that are free, yet the banker refuses it: it would leave \((2,1,0)\) free. P1, the only process whose need fitted before, still needs \((0,2,0)\), and with one unit of the second type free no process's need would fit. There are no safe orders afterwards. Nothing is deadlocked at that point, but if every process then asked for its full claim, none could proceed.

    Two processes, one resource

    With one resource type of \(T\) units and two processes with claims \(M_1,M_2\le T\), the state is the pair of allocations \((a_1,a_2)\) with \(a_1+a_2\le T\). Process 1 can finish from here if \(M_1-a_1\le T-a_1-a_2\), that is \(a_2\le T-M_1\); after it releases, process 2 has all \(T\) units and finishes too. Symmetrically for process 2. So

    \[\text{unsafe}\iff a_1>T-M_2\ \text{ and }\ a_2>T-M_1 ,\]

    a rectangle in the corner of the triangle of feasible states. With unit requests, a deadlock is a state where no unit is free and neither process has its full claim, \(a_1+a_2=T\), \(a_1<M_1\), \(a_2<M_2\): the edge of the rectangle on the line \(a_1+a_2=T\). The block classifies every state for \(T=10\), \(M_1=7\), \(M_2=6\) with banker_safety() and deadlocked_processes().

    Feasible states: 50. Safe: 47. Unsafe but not deadlocked: 1. Deadlocked: 2. Closed form agrees with the safety algorithm on 50 of 50.

    Of the 50 feasible states, 47 are safe, one, \((5,4)\), is unsafe but not deadlocked, and two, \((5,5)\) and \((6,4)\), are deadlocked: no unit is free and each process still needs more. The closed form agrees with the safety algorithm in all 50 states. The orange state shows why avoidance must look ahead. At \((5,4)\) one unit is free and either process may take it, but whichever does, the system lands on a red state. The banker refuses both requests at \((4,4)\) and \((5,3)\) that would enter \((5,4)\), so the unsafe corner is never entered. The safe region is large because the claims are modest; with \(M_1+M_2\le T\) the rectangle would be empty and every state safe.

    What avoidance costs

    simulate_resource_allocation() runs four processes with claims (3, 2), (2, 3), (3, 3) and (2, 2) on two resource types. Each repeatedly runs jobs: it acquires its claim one random unit at a time, then releases everything. At each step a random process acts. Under grant-if-available a request is granted whenever a unit is free; under the banker it is granted only if the result is safe. The block varies the number of units of each type from 3 (the largest single claim) to 10 (the sum of the claims) and runs each policy 200 times for 5,000 steps.

    With 7 or fewer units of each type, every one of the 200 greedy runs deadlocked, in a median of 8 steps with 3 units and 116 steps with 7. With 8 units, 190 of 200 still did, though only after about a thousand steps. With 9 or 10 units no run deadlocked within 5,000 steps; at 10 the units cover every claim at once and deadlock is impossible. The banker never deadlocked at any size, as the theory guarantees.

    The price is refused requests: with 3 units the banker refused 7.5 requests for every completed job, falling to almost none once resources are plentiful. Surprisingly, the banker also completes more jobs per step while running, 55 against 9 per thousand steps at 3 units. The greedy policy spends its steps in unsafe states, with processes holding units and waiting on each other until the system freezes, while the banker keeps the resources with processes that can finish, which also shows in its higher utilisation (0.67 to 0.80 against 0.55 to 0.66). Once the units suffice, both policies behave the same.

    The catch, which limits the banker's use in practice, is the assumption behind it: every process must declare its maximum claim in advance, and the number of processes must be fixed.

    Summary

    • A state is safe when some order lets every process obtain its full remaining claim; a safe state cannot deadlock, and the greedy check finds a safe order whenever one exists, because finishing a process only frees resources.
    • The textbook instance has 16 safe orders out of 120. The banker grants P1's request (8 safe orders remain) and refuses P0's request for free units because no safe order would remain.
    • For two processes and one resource type the unsafe states form the rectangle \(a_1>T-M_2,\ a_2>T-M_1\), and the deadlocks lie on its edge where no units are free.
    • In simulation, granting whatever is free deadlocked every run when resources were tight; the banker never deadlocked and completed more jobs per step, at the cost of refusing requests.
