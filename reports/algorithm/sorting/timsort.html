    Timsort: actual natural runs, extension and stable merge stacks

    Abstract

    Adaptive sorting detects order already present in the input, extends short runs, and merges adjacent runs stably. Actual sorting events and the shared native raw-run detector distinguish the original input profile from the runs consumed after extension.

    Mechanism and mathematical scope

    Nondecreasing runs retain equal-key order; only strictly descending runs are reversed. Binary insertion uses an upper bound for equal keys, and merges prefer the earlier left run on ties. Minrun is computed by shifting until below64 and retaining discarded low bits. Merge-collapse checks include both the top-three and next-deeper inequalities; this repairs the old top-three-only policy. Galloping is omitted. The standard run-stack strategy gives adaptive stable O(n log n) worst-case comparison behavior and a linear scan on already ordered input. Raw input run count is not the count of runs consumed after short-run extension.

    API and interpretation

    Copyable strict-weak-order keys are supported; nonfinite built-in floating values reject. The in-place compatibility sort replaces caller data only on success. Full int index/key geometry and actual comparisons/assignments/history policies are checked. The shared raw-run detector is used by both input profiling and the actual sort, and only producer events claim actual sorting states.

    Reusable producers, fixtures and histories live in the canonical C++ library. Captured records own their values and do not come from a separate report replay. Selected counters and record/scalar policies are specified at their API boundaries; they are not peak-byte or wall-time budgets. Synthetic structural inputs are controlled fixtures for these mechanisms.
