    Signed radix sort: actual byte passes and stable origin identities

    Abstract

    A signed integer sort can exploit fixed-width digits rather than compare arbitrary key pairs. The native LSD radix producer flips the sign bit, stably scatters one byte at a time and restores signed values after eight passes. This report reads actual histograms, prefix offsets and original input identities. The original eight positive keys and signed-key example remain; the old decimal report mirror is replaced by the library actual base256 passes.

    Mechanism and mathematical scope

    Two's-complement signed order becomes unsigned order under \(u=\mathrm{uint64}(x)\mathbin\oplus2^{63}\). For byte r, count its occurrences and prefix-sum the counts to obtain each bucket start. Scattering in input order increments each bucket cursor, preserving order among equal current digits.

    \[\operatorname{stable\_sort}_{d_r}\circ\cdots\circ\operatorname{stable\_sort}_{d_0}\]

    Induction on processed bytes proves ordering by the low r+1 bytes. The eighth pass therefore orders all biased words, and undoing the bias recovers ascending signed keys. The producer moves original indices beside keys; equal final keys retain increasing original indices. For n>=2, actual work includes16n digit reads,8n scatter pairs and2048 prefix updates, excluding allocation and sign conversion. Fixed-width cost is \(O(8(n+256))\), with linear scratch storage; empty and singleton inputs skip all passes.

    API and interpretation

    The original decimal illustration is not labelled as native work: its input is retained and shown through the canonical byte producer instead. Intermediate signed decodings need not be sorted until the eighth pass; actual origin identities prove stability at every pass. The original1000-trial signed/extreme std::sort cross-check moves to native regression verification. Fixed eight-pass linearity is specific to64-bit keys and radix256, not a contradiction of the comparison-sort lower bound. History stores actual keys/origins plus bucket data and is independently bounded.

    Reusable producers, fixtures and histories live in the canonical C++ library. Captured records own their values and do not come from a separate report replay. Selected counters and record/scalar policies are specified at their API boundaries; they are not peak-byte or wall-time budgets. Synthetic structural inputs are controlled fixtures for these mechanisms.
