    Bitonic Sort: A Fixed Network with Visible Comparators

    Abstract

    Given an unordered sequence, sort it using comparison locations determined only by its length. A fixed network exposes independent comparison stages, while the values decide which exchanges occur. We inspect a four-wire execution, retain the original eighteen-element example, derive exact power-of-two comparison counts, and exhaust binary inputs to check the zero-one principle. The sorter, network inspector and execution trace share one canonical comparator traversal.

    The method

    A compare/exchange operation sends the smaller and larger of two values to specified wires. A bitonic sorter recursively sorts opposing halves, then merges the resulting bitonic sequence. For power-of-two length n, the merge first compares wires separated by n/2 and then merges the two halves.

    For zero-one input, a cyclic bitonic sequence has one contiguous block of ones on a circle. Comparing opposite positions separates the smaller from the larger half, leaves each half bitonic, and ensures every value in the first half is at most every value in the second. Recursing establishes the merge; recursively forming the opposing sorted halves establishes the sorter.

    The wire pairs and directions depend only on n. They form a sorting network, and comparisons in a dependency stage use disjoint wires. The native C++ sorter executes them sequentially; a stage label is an available parallel schedule, not a measurement of threads or GPU execution.

    Arbitrary lengths need the right merge invariant

    The implementation follows Lang's generalisation. Let s be the greatest power of two strictly below n. Compare \((i,i+s)\) only while both wires exist, then recurse on lengths s and n-s. Ascending sorting first builds a binary valley, \(1^*0^*1^*\), from a descending left part and ascending right part. Padding that valley with ones preserves its shape; comparisons against the padded ones do nothing. The power-of-two merge therefore restricts to the real wires, leaving a power-of-two bitonic left part and a valley-shaped right part for recursion. Descending sorting has the symmetric zero-padding argument. This is not a claim that every arbitrary-length cyclic bitonic input can be merged by this restricted operation.

    Checking the theory: exact counts

    For \(n=2^p\), a merge has p layers and n/2 comparisons per layer. If M is merge work and C is sorting work,

    \[M(n)=\frac n2\log_2n,\qquad C(n)=2C(n/2)+M(n)=\frac n4p(p+1),\qquad D(n)=\frac{p(p+1)}2.\]

    The formula follows by summing the merge work at each recursive level. The leading term \(np^2/4\) omits \(np/4\); it is not the exact count. For arbitrary n, the emitted network gives the actual comparison count. Its depth is \(q(q+1)/2\) for \(q=\lceil\log_2n\rceil\), with zero depth for n=0 or n=1, and at most \(\lfloor n/2\rfloor\) comparisons per stage.

    The zero-one principle and value-dependent swaps

    Thresholding commutes with min and max. If a comparison network left an inversion between two ordered values, a threshold between them would leave an inverted binary pair. Hence a network that sorts every binary input of length n sorts every totally ordered input of that length. Finite exhaustive checks validate those sizes; the recursive argument establishes the construction's general correctness.

    Conclusion

    One canonical visitor now supplies sorting, comparator counts, dependency stages and recorded compare/exchange events. The original eighteen-element example sorts without padding the caller's vector. Exact counts and exhaustive binary controls support the network description, with generated inputs sufficient for these ordering properties.

    The native implementation remains sequential and uses branches and exchanges that depend on values. Fixed comparator locations do not establish constant-time execution. The sort is not stable; descending comparisons retain the historical exchange-on-equality rule. The unrecorded sorter uses a logarithmic recursion stack, while materialising a topology or trace adds storage proportional to the number of comparisons. No observed dataset or runtime speed claim is needed.
