    Sørensen–Dice Similarity: Shared Byte Bigrams, Multiplicity and Lost Order

    Abstract

    Given two strings, we want a small score describing how much adjacent local structure they share. Repeated pieces must count correctly, and a high score must not be confused with string equality or semantic equivalence. The Sørensen–Dice coefficient normalizes multiset bigram overlap into a similarity between zero and one. We first expose the actual shared pair in night/nacht, then reproduce all five original word-pair scores. Native count and consumption APIs reveal why aa/aaaa scores one half, why different strings can score one, and why one minus Dice is not a metric. Literal-byte and short-string controls make the encoding convention explicit. A repeated-byte family checks the closed forms for Dice, multiset Jaccard and occurrence-level work without claiming those counts measure hash probes or elapsed time.

    Begin with one shared pair

    The string night has four adjacent byte pairs: ni, ig, gh, ht. The string nacht has na, ac, ch, ht. Only ht is shared. Each side has four occurrences, so their multiset intersection has size one and

    \[D(\texttt{night},\texttt{nacht})=\frac{2\times1}{4+4}=\frac14.\]

    The native trace builds left counts, then looks up right occurrences in input order. A successful lookup consumes one remaining left occurrence. Its rows are sorted by an unsigned two-byte key; its events retain the actual right positions and before/after counts. Nothing is recovered by replaying the algorithm. This first input has no repeated keys, so its one successful consumption is especially easy to check.

    Derive the multiset normalization

    For each possible byte pair g, let c_a(g) and c_b(g) be its occurrence counts. Use A and B for their totals, I for the intersection and U for the union:

    \[A=\sum_g c_a(g),\quad B=\sum_g c_b(g),\quad I=\sum_g\min(c_a(g),c_b(g)),\quad U=\sum_g\max(c_a(g),c_b(g))=A+B-I.\]

    A byte string of length k contributes max(k−1,0) occurrences, without boundary padding. When A+B is positive, Dice and multiset Jaccard are

    \[D=\frac{2I}{A+B},\qquad J=\frac I{A+B-I},\qquad D=\frac{2J}{1+J},\qquad J=\frac D{2-D}.\]

    Because I≤min(A,B), the exact ratio lies between zero and one. For positive combined size, score one means equal occurrence counts at every key; it does not recover global character order. The same fact follows by rewriting

    \[D=1-\frac{\sum_g|c_a(g)-c_b(g)|}{A+B}.\]

    For nonzero I, treating I/B as precision and I/A as recall gives D as their harmonic mean. The algebra concerns these counted features, without asserting that either string is a correct label or that the result is a match probability. The Dice/Jaccard transform is increasing, so it preserves pair rankings when both scores use the same multiset features and the same empty convention. Using sets of distinct bigrams would change the features and the answers.

    Two zero-sized bigram bags need an explicit convention. The established scalar API gives one for identical strings, including empty and one-byte strings, and zero for any other comparison involving a string shorter than two bytes. In particular a/b scores zero although both bigram bags are empty. The trace retains that string-level convention. The count-only API cannot know the original strings, so its empty_equal argument explicitly chooses zero or one.

    [Dice's 1945 paper](https://doi.org/10.2307/1932409) introduced an ecological coincidence index with the normalization 2h/(a+b). The byte-bigram construction here is a later lexical use, not a claim about that paper's original algorithm. [Kondrak, Marcu and Knight](https://aclanthology.org/N03-2016/) use character bigrams for word similarity; datamunge specifies literal bytes and multiplicity explicitly. The historical name Sørensen–Dice does not imply Unicode handling.

    Multiplicity, lost order and a failed triangle inequality

    The string aa has one occurrence of aa, while aaaa has three. Only one can be consumed from the left, giving D=2/(1+3)=1/2 and J=1/3. Treating the bigrams as sets would instead produce one. Conversely, abaca and acaba have the same four bigrams, ab, ba, ac and ca, in different orders: their score is one despite different strings. This is a feature collision, not a numerical error. Literal case, spaces, punctuation and embedded NULs also remain part of the input. Canonically equivalent UTF-8 spellings can have different byte bigrams; neither character decoding nor normalization is performed here.

    The dissimilarity d=1−D is symmetric and nonnegative but is not a metric. Besides the equality collision, three tiny strings violate the triangle inequality: ab and bc share no bigram, while each shares one of abc's two. The following diagram's edge values come from actual scalar calls.

    Check work and closed forms on repeated occurrences

    Take a=a repeated k times and b=a repeated 3k times, with k≥2. There is only one distinct bigram key. Its multiplicities are A=k−1 and B=3k−1, so I=k−1, U=3k−1 and

    \[D_k=\frac{k-1}{2k-1}\longrightarrow\frac12,\qquad J_k=\frac{k-1}{3k-1}\longrightarrow\frac13.\]

    The trace's actual occurrence-level operations are k−1 left updates and 3k−1 right lookups, totaling 4k−2. It consumes k−1 occurrences and records 2k misses, even though all right bigrams have the same key. Its event list has 3k−1 entries; complete A+B caps include both sides. The plot explicitly transforms its horizontal axis to log2(k), and its work axis to log2(count). The table keeps untransformed integers. These are dictionary operations at the occurrence level, excluding hash probes, collisions, rehashing, copying and trace sorting; they are not elapsed-time measurements.

    Implementation, checks and limits

    The canonical core now packs each unsigned byte pair into a 16-bit key and uses size_t occurrence counts. It reserves capacity for at most 65,536 left keys, rather than constructing a temporary substring key for each update or reserving in proportion to a long input beyond the finite byte alphabet. Counts remain exact integers; normalized scores use binary64 rounding. Hashing gives expected O(ab) scalar work and O(min(a,65536)) auxiliary storage. Adversarial collision behavior can increase hash-table work. The rich trace additionally sorts K distinct union keys in O(K log(K+1)) and owns both input strings and one event per right occurrence. Its total storage is O(ab+K), with K≤65,536. Scalar identical/short inputs retain their early return; the trace scans even those inputs so that its reported work and rows are actual. Default complete occurrence cap is 1,000,000; zero disables only that cap. Count-sum arithmetic remains checked, and failures return no partial trace. Neither the count-only test above nor these bounds claim that multi- gigabyte strings were materialised.

    Independent tests compare sorted token-list intersections/unions and a separate unconsumed-token scan against 29,282 exhaustive small ASCII/binary pairs and 2,000 seeded byte-string pairs. A bijection renaming all bytes preserves the score. A 131,072-byte control contains every one of the 65,536 byte pairs and checks unsigned sorting, counts and complete matching. A larger unary control checks 100,000 successful and 200,000 failed consumptions. Count-only tests exercise size_t boundaries without enormous allocation. Original scores, short conventions, case/space/NUL/UTF-8 controls, equal-feature collisions, triangle failure, exact caps, ownership and overflow/error precedence are checked separately. No external dataset is needed for these finite controls.

    The result measures shared local byte structure. It is useful as an explicitly chosen feature score, but cannot establish string identity, Unicode equivalence, meaning, edit distance or a metric geometry. Preserve multiplicities and choose any preprocessing before constructing the byte strings; the score itself makes none of those decisions.
