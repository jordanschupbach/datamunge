    The Z-Algorithm: Reusing Prefix Matches to Guarantee Linear Work

    Abstract

    The Z-array records how much of a string's prefix reappears at every position. Maintaining the rightmost known prefix-match interval lets the algorithm reuse earlier answers, limiting explicit equality tests to at most twice the input length. We derive that invariant, inspect an actual trace, and reduce exact substring matching to a virtual sequence with a separator outside the byte alphabet. The application searches dm::datasets::titanic() passenger names independently and records both matches and actual comparison work. A repetitive-string check contrasts the linear algorithm with the quadratic work of naive prefix matching.

    The data: separate passenger-name strings

    The Titanic frame contains 891 passenger records and 12 columns. We use its Name column directly, preserving case and punctuation. Titles such as Miss. and Mrs. provide frequent exact queries, while William and Anna also illustrate matches within other parts of a name. These are byte-substring searches, not a parser for titles or given names.

    The method: one prefix question at every position

    For a sequence \(S\) of length \(n\), define

    \[Z[i]=\max\{k:0\le k\le n-i,\ S[0,k)=S[i,i+k)\}.\]

    This implementation sets \(Z[0]=n\); some conventions leave it zero. A naive algorithm compares the prefix separately against every suffix. For \(S=a^n\), its comparisons total \(n(n-1)/2\), even though the answers have an obvious repeated structure.

    The Z-algorithm maintains a half-open interval \([\ell,r)\), the rightmost prefix-match box discovered at positions already processed: \(S[\ell,r)=S[0,r-\ell)\). The operational scan starts at position one with an empty box, independently of the \(Z[0]=n\) convention. At the next position \(i\), choose a starting match length

    \[b_i=\begin{cases} 0,& i\ge r,\\ \min\{r-i,Z[i-\ell]\},& i<r. \end{cases}\]

    The mirror index \(i-\ell\) is smaller than \(i\), so its answer is already available. Capping at \(r-i\) prevents us from claiming anything past the verified box. Starting from \(b_i\), compare symbols until a mismatch or the sequence end, then replace the box by \([i,i+Z[i])\) when that reaches farther right.

    Why reuse is correct

    If \(i<r\), the box identity copies the relevant region back into the prefix. When \(Z[i-\ell]<r-i\), its terminating mismatch also lies inside the box and transfers to the new position: the copied answer is already exact. The shared library loop may perform that one known failing test, but it cannot gain a successful extension there.

    If \(Z[i-\ell]\ge r-i\), only the remaining box length is established; further comparisons must start at the old right edge. Outside the box, no characters can be reused. In every case, the seed is valid and direct extension finds the exact answer.

    Why the comparison count is linear

    Every successful explicit comparison reaches beyond the old right edge; no later position needs to verify that same extension of the frontier again. There are at most \(n-1\) such successes. Each processed position can terminate with at most one failing equality test, giving

    \[C_{\rm success}\le n-1,\qquad C_{\rm fail}\le n-1,\qquad C\le2(n-1)\quad(n>0).\]

    Bounds checks and loop bookkeeping add constant work per position. Thus time and Z-array storage are \(O(n)\), even for highly repetitive inputs. The counters below measure equality tests from the actual loop; they are not estimates from another implementation.

    Exact search with a separator that cannot be a byte

    For pattern \(P\) of length \(m\) and text \(T\) of length \(n\), consider the virtual sequence

    \[S=P\;\Vert\;\langle256\rangle\;\Vert\;T.\]

    Every input byte is interpreted as an unsigned value from 0 to 255, so the sentinel cannot equal any input symbol. For an index \(i\ge m+1\) in the text region, \(Z_S[i]=m\) exactly when a complete pattern begins at text offset \(i-m-1\). The sentinel prevents an extension beyond \(m\). All overlaps are retained.

    The library accesses this conceptual sequence without copying a joined string. It stores the Z-array, giving \(O(n+m)\) time and temporary storage for one fitting nonempty pattern. Unlike the old fixed-byte separator contract, no input byte is reserved. Empty patterns keep the existing API convention of matching every boundary \(0,\ldots,n\), with no preprocessing; a pattern longer than the text also returns early.

    Applying it to every passenger name

    Each name is searched as a separate record. In particular, a query cannot match the end of one surname followed by the beginning of another record. The work size includes each record's virtual pattern and sentinel when preprocessing runs. A sum of per-record linear bounds provides a direct check of the implementation's guarantee.

    Searching six patterns independently repeats preprocessing six times. For a large dictionary, an automaton such as Aho–Corasick can share work across patterns. Conversely, the right-to-left skipping methods in the Zhu–Takaoka report can use fewer comparisons on short names even without Z's worst-case linear guarantee. Comparison counts alone do not include allocation, cache behaviour or wall-clock time.

    A repetitive worst case for naive preprocessing

    For \(a^n\), the first shifted prefix match extends through \(n-1\) symbols. Every later match is copied to the end from the established box, so the Z-algorithm makes exactly \(n-1\) equality tests. The naive method repeats the already-known suffix matches:

    \[C_Z=n-1,\qquad C_{\rm naive}=\sum_{i=1}^{n-1}(n-i)=\frac{n(n-1)}2.\]

    Conclusion

    The Z-box makes verified equality reusable: a copied seed is capped by the known interval, and any new successful tests advance its frontier. Instrumentation connects that invariant to the linear comparison bound. The same preprocessing gives exact byte-substring search with overlaps and no reserved input symbol. Passenger-name queries provide a real record-wise application; repeated-byte strings verify the case where naive preprocessing wastes the most already-known work.
