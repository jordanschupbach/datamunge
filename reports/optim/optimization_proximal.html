    Proximal Gradient and FISTA: Loss, Thresholds and Stationarity

    Abstract

    A regression loss with an L1 penalty is convex but nonsmooth at zero coefficients. Ordinary smooth-gradient stationarity is therefore the wrong stopping target. We derive the proximal update and its soft-threshold map, check a two-coordinate solution, and show a rate that is stable for plain gradient steps but unstable for acceleration. Iris then supplies a matched raw-unit objective, compared with the independent coordinate-descent Lasso implementation across penalties.

    The method

    Write F=f+g, where f has a Lipschitz gradient and g has an accessible proximal map. A quadratic upper model of f gives the proximal-gradient step. For the L1 penalty, each penalised coordinate has the soft-threshold solution:

    \[x^+=\operatorname{prox}_{\eta g}(x-\eta\nabla f(x)),\qquad \operatorname{prox}_{\eta\lambda|\cdot|}(z) =\operatorname{sign}(z)\max(|z|-\eta\lambda,0).\]

    The threshold follows by solving z-w+eta*lambda*sign(z)=0 in the positive and negative regions and checking the zero subgradient interval. An unpenalised intercept passes through unchanged. The library interface's gradient supplies only the smooth part; evaluate returns the entire composite objective.

    ISTA repeats that map. FISTA instead evaluates gradients at extrapolated y points, uses t_next=(1+sqrt(1+4*t squared))/two and y_next=x_next+(t-1)/t_next*(x_next-x). With a convex f, convex g and eta<=1/L, the standard accepted-iterate objective bounds are O(1/k) for ISTA and O(1/k squared) for FISTA. Those bounds do not assert that FISTA's extrapolated-point objective is monotone. This implementation has no backtracking, adaptive restart or monotone safeguard. Both stop on coordinate displacement; the post-run mapping is

    \[G_\eta(x)=\frac{x-\operatorname{prox}_{\eta g}(x-\eta\nabla f(x))}{\eta}.\]

    For a convex problem, G_eta=zero is an optimality condition. A small coordinate change with a tiny rate need not imply a small mapping. Neither solver requests full objective values inside its loop: the recorder samples gradient-request points afterwards, and the final returned point is checked separately. Dense least-squares gradient cost is O(n*p), with O(p) optimizer state beyond the design.

    Small worked example

    A two-coordinate lasso solution and its threshold map

    Let f=.25*((x0-3)2+(x1+1)2) and g=.5*(abs(x0)+abs(x1)). The exact solution is (2,0), with F=1.5. At this point the smooth gradient is (-.5,.5), not zero, but soft thresholding x-gradient(x) at .5 returns x unchanged. From the origin with eta one, ISTA's first point is (1,0) and after k steps x0=2*(1-2 to the -k), while x1 remains zero. The returned four-step point is (1.875,0). Gradient-request samples describe pre-update points for ISTA and look-ahead points for FISTA.

    Checking the rate assumption

    A rate stable for ISTA need not be stable for FISTA

    Use the smooth special case F=.5*x squared, lambda=zero and L=one. Plain ISTA is gradient descent, so eta=1.5 still contracts by -0.5. FISTA's extrapolation can be unstable at that same rate, which violates the standard eta<1/L assumption. Compare eta.5 and 1.5 over thirty updates from x=one.     Conclusions and references

    The exact threshold map and two-coordinate optimum show why the smooth gradient can remain nonzero at a correct lasso solution. The rate counterexample qualifies acceleration claims, and the Iris analysis matches scaling, intercept and penalty before comparing numerical solutions. A small displacement or a flat requested-point loss curve is supplemented by the proximal mapping norm. These training-objective checks do not estimate predictive generalisation or regularisation-selection uncertainty.

    • A. Beck and M. Teboulle (2009), [A Fast Iterative Shrinkage-Thresholding Algorithm for Linear Inverse Problems](https://doi.org/10.1137/080716542).
    • J. Friedman, T. Hastie and R. Tibshirani (2010), [Regularization Paths for Generalized Linear Models via Coordinate Descent](https://doi.org/10.18637/jss.v033.i01), the separate reference solver family.

    Reading the numerical evidence

    trace_optimize calls the configured native optimizer through its stated abstract interface. It records callback requests without inserting fitting evaluations. Value calls can be rejected trials; gradient calls can be look-ahead points. optimization_comparison explicitly re-evaluates selected points afterwards on these pure objectives. Those diagnostic calls are excluded from fitting counts. Callback indices are neither accepted iterations nor wall time. The plotted gap uses the declared reference (minimum or stated lower bound) and a display floor of 1e-14; that floor does not modify any optimizer update. Returned coordinates, checked objective and appropriate stationarity/feasibility checks carry more information than a return from a finite iteration budget. Native APIs do not expose a uniform stop-status flag. The recorder retains exceptions and rejects nonfinite requested values/gradients; this makes failures visible rather than letting an instrumented run continue on NaN.
