    Breadth-First Search: FIFO Layers and Minimum-Edge Paths

    Abstract

    Breadth-first search removes vertices from a FIFO queue, marking each vertex when it is first enqueued. That ordering makes every discovered distance a minimum number of edges from the start. We inspect a small graph's actual queue and predecessor choices, retain the original three-vertex example, and distinguish a discovered vertex from one already dequeued. Generated four-neighbour grids provide a closed-form distance check and exact adjacency work counts. Path, distance and queue records come from one canonical C++ loop.

    A small graph: the first predecessor fixes the path

    Start at vertex zero and seek vertex five. The start enqueues one before two. They subsequently enqueue three and four, so three is processed first and claims five's predecessor. When four later reaches five, that vertex is already marked and is not enqueued again. Both routes have three edges; the input adjacency order selects path 0–1–3–5 deterministically.

    Why first discovery gives a shortest-hop distance

    The start has distance zero. When a vertex at distance k is removed, each new neighbour is assigned distance k+1 and appended to the queue's tail. All earlier entries remain ahead of those discoveries. Inductively, dequeue distances never decrease, and a vertex cannot first receive distance k+1 if a shorter path exists: its predecessor on that shorter path would already have been removed and would have discovered it earlier.

    Store the first-discovery predecessor once and follow those links backwards from the goal to reconstruct a minimum-edge path. This solves a unit-cost problem. It does not minimise arbitrary edge weights. Different input orders can select different equally short paths while preserving the hop distance. Loops and parallel edges are allowed; they are inspected but cannot re-enqueue vertices whose distances have already been assigned.

    Original example and stopping-time controls

    The original chain has three vertices and edges 0→1→2. Its returned path has three vertices and two edges. Input is directed by default; setting directed false inserts both orientations. An unreachable goal returns an empty path, while start=goal returns the single starting vertex after its dequeue.

    The final control shows why the trace's distance sentinel means undiscovered at stopping time. For edges 0→1, 0→2, 1→3 and 2→4, seeking goal two removes zero, one and two. Vertex three has already been discovered at depth two and remains queued. Vertex four is still undiscovered because the goal's outgoing edge is not expanded, even though four is reachable in the full graph.

    Predecessor sentinel n is used for the start and for undiscovered vertices. Distance sentinel n is not a valid finite hop distance: any shortest simple path has at most n-1 edges. If the goal is unreachable, queue exhaustion does explore every vertex reachable from the start. Every discovered vertex then has its full-graph minimum distance, and all other vertices are unreachable. Both terminals and every edge endpoint must lie in [0,n); an empty graph therefore has no valid call. Validation still checks every edge when start=goal.

    Grid layers and complete adjacency work

    The existing native grid generator labels cell (r,c) as r*cols+c and connects horizontal/vertical neighbours. From the upper-left corner, the minimum-hop distance is r+c: each step changes at most one coordinate by one, and a path with r downward and c rightward moves attains that lower bound.

    Use an 8 by 10 grid and request the native full traversal from its upper-left corner. This entry point exhausts all reachable vertices without a target.     Time, memory and the cost of a trace

    Each vertex is enqueued at most once and removed at most once. Scanning a removed vertex examines its adjacency entries, including duplicates and loops; the goal's entries are excluded because removal stops the search. Validation and graph construction still inspect the complete input edge list. Thus total work is O(n+E), with E directed entries or 2E entries for undirected input.

    Queue, distance, predecessor and result arrays use O(n) storage. Because this API accepts an edge list and builds its own adjacency lists, total owned working storage is O(n+E), rather than only the search arrays' O(n). The ordinary function allocates no trace events. A trace without queue snapshots adds only linear event storage: total discoveries are at most n-1.

    By default, a trace also copies the active queue before every removal. If Q is the sum of those queue lengths, this adds O(Q) time and storage; a wide star can make Q quadratic. Passing capture_queue=false preserves the linear bound while retaining actual lengths, discoveries, distances and counters. All returned data are owned, inputs are unchanged, and independent calls share no mutable state. Generated graphs provide the hand-checkable structural examples here; no observational dataset is required.
